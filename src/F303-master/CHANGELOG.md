# Changelog - Firmware (`src/F303-master/`)

Firmware and bootloader are versioned and released independently -
flashing a new bootloader doesn't imply a new application version and
vice versa, so each gets its own history. The bootloader's own
changelog lives at [`boot/CHANGELOG.md`](boot/CHANGELOG.md).

| Version | Notes |
|---|---|
| **0.2.5** | New "black box" fault recorder (`firmware_blackbox.c`/`.h`) - audit idea: "sistema de Black Box en la F-RAM para registrar los últimos 10s antes de un error" (SONNET/AUDITORIA_COMPLETA_44_PROYECTOS.txt). A continuously-updated 67-sample RAM ring buffer (~10.0s at the same 150ms cadence `Render_ToolScreen()` already runs on - `tick_ms`/`active_tool`/`current_temperature`/`target_temperature`/endstop+error flags per sample), flushed to a new F-RAM region (`BLACKBOX_FRAM_ADDR` 256, well past `SavedState_t`'s own footprint at address 0) exactly once per real fault - the rising edge of `system_error_flag`, latched so a fault that stays true doesn't let every later tick overwrite the pre-fault window with nothing-but-already-faulted samples, and re-armed if the flag ever clears. Same CRC-8/SMBUS record-integrity pattern `SavedState_t` already uses. Readback over CAN deliberately NOT implemented this pass (0x1A8/0x1A9 would be the natural next free global-command pair) - a chunked-transfer protocol for ~680 bytes deserves its own focused review, not to ride along unverified; the capture itself is independently valuable and inspectable via ST-Link/a F-RAM dump tool without it. Verified with a real `build_firmware.sh` (17/17 passed, 0 warnings) plus a standalone host-side simulation of the ring-buffer/edge-detection logic (faithful line-by-line translation of the real C) confirming exactly one flush per real fault occurrence, correct re-arming after the fault clears, and a second fault later correctly flushing again - not verified against real F-RAM hardware (no board available this session). |
| **0.2.4** | New `OLED_DrawTempSparkline()` (`firmware_render.c`/`.h`) - a rolling ~60s temperature-trend sparkline on page 4 of the soldering iron's own tool screen, the only page left genuinely unused there (confirmed via grep - no other `OLED_SetCursor(4, ...)` call anywhere in this file). Audit idea: "gráficas de temperatura en tiempo real en el OLED" (SONNET/AUDITORIA_COMPLETA_44_PROYECTOS.txt). Internally rate-limited to one real history sample every ~2s (its own 32-slot circular buffer) so the visible trend spans a real time window rather than being dominated by noise between consecutive 150ms `Render_ToolScreen()` calls. Verified with a real `build_firmware.sh` run (17/17 passed, 0 warnings) plus a standalone host-side simulation of the value-to-pixel-column math (Python, faithfully replicating the C for-loop's exact semantics) confirming correct output at the min/max/quarter-scale boundaries and full monotonicity across the whole 0-450°C range - not verified against a real physical OLED (no board available this session). |
| **0.2.3** | Verification build confirming the boot-splash regeneration below still compiles clean. No further source change. |
| **0.2.2** | Regenerated `SplashYellowText`'s own version-text half (`firmware_render.c`, columns 74-127 of the yellow strip) to fit this version scheme's own digit count - the "URTC" wordmark half (columns 0-73) is untouched, byte-identical to before. `ani/splash_boot.gif` (documentation preview only, not compiled into firmware) regenerated to match. |
| **0.1** | Project-wide version migration: both PC tools and this firmware/bootloader's own source folder move from `V0.0/` to `V0.1/` (`tools/flasher/`, `tools/tester/`, `src/F303-master/`). Compiled firmware binaries renamed to match (`URTC_V0.1_F303CC.bin/.hex/.elf`). No functional firmware changes beyond what's already listed under 0.0 below - this bump is the migration itself. The bootloader is unaffected by this migration and keeps its own independent version numbering (see its own changelog) - only its folder moved alongside the firmware's. Later, still within this same version (no version bump, per this project's own rule that the firmware's version only changes on explicit request): IDs 12-24 assigned to the 13-tool expansion catalog (see the unified Tool Catalog section in the main README), landing tool by tool - `TOOL_INVALID` moved to 25 to make room, and the `0x0C-0x1B`-style ID range check extended accordingly. The new companion expansion-slave chip (STM32F303CBT6, `src/F303-slave/`) got its own bootloader and application firmware, versioned entirely independently of this firmware (see [`src/F303-slave/CHANGELOG.md`](../F303-slave/CHANGELOG.md)). Later still, within this same version: the monolithic single-file build (this project's earlier dual-form maintenance approach) was retired in favor of maintaining a single source form - what had lived in `partitioned/` moved up to `src/F303-master/` directly (and `src/F303-master/boot/`, `src/F303-slave/`, `src/F303-slave/boot/` for the rest of this project's firmware), the `V0.1/` version-numbered subfolder dropped from every path in the process. No functional change - this is a source-tree reorganization, not a firmware behavior change. Later still, within this same version: 2 new expansion board variants (Basic+ADS1115, Basic+MLX9064x - `expansion_board_type` 5/6) get an ADS1115 and any of the 3 MLX9064x-family sensors wired directly to this board's own bit-banged expansion I2C bus, no slave MCU involved - `firmware_ads1115.c` and 3 new `melexis_mlx90640/mlx90641/mlx90642/` folders, with `Handle_CAN_FlyingProbe()`/`Handle_CAN_ThermalInspection()` both branching on `expansion_board_type` (and `mlx_sensor_variant` for the thermal sensor) to reach either this board's own direct driver or the expansion slave chip's own relayed one, transparently to whatever host is talking to them. A real bug from an earlier tool-count update was also found and fixed here: `0x1A2`'s own validation still capped `free_tool_selection` at 12 despite this project's own comment already saying 25 - silently rejecting any of the 13 newer tools in that specific configuration path. Later still, within this same version: the Soldering Iron gained its own motorized wire feeder, spooling solder wire into the joint - reuses `CONN_MOT` and the plain-stepper `0x120` protocol already shared by 7 other tools (`firmware_can_dispatch.c`'s own `TOOL_SOLDERING_IRON` case now calls both its own heater handler and `Handle_CAN_MotionTools()`), plus 2 new commands of its own (`0x131` reset, `0x132` query/response) for an open-loop position estimate persisted across power cycles (`SavedState_t`'s own `solder_spool_position`, `SAVEDSTATE_VERSION` 6→7, 30→34 bytes). Traded away in the process: this tool's own generic endstop input on `CONN_SEN`, since its `PB3` line is the same physical pin the feeder's own STEP output needs - a deliberate hardware trade-off, not an oversight, made at the project owner's own explicit choice once the conflict was found. `0x135`'s own telemetry frame dropped from DLC 3 to DLC 2 as part of this - its old 3rd byte is removed for Hot Air Rework too, since a real, independently-found bug meant that tool's own copy of this byte never actually reported a real endstop reading in the first place (`TOOL_HOTAIR_REWORK` was never in the endstop-polling tool list to begin with). Later still, within this same version: a firmware-wide audit found and fixed several defects - `SavedState_MaybeSave()`/`SavedState_Load()` now actually save and restore `solder_spool_position` and `mlx_sensor_variant` (both were already documented as persisted, but never wired into either path); `hmac_chunks_received` (`firmware_can_slavebridge.c`) now resets on `0x211` rather than only after a complete 4-chunk sequence, so an aborted slave-update retry can't corrupt the next attempt's HMAC; the boot-splash watchdog mirror now includes `Watchdog_Safety_HotendFan()`, matching every other tool on that same list; UV Curing (`0x1D0`) and Hot Air Rework's own blower now have their own communication watchdogs (250ms and 1000ms respectively), matching every other actuator sharing `TIM1_CH1`; `weld_pulse_duration_ms` (`0x1C0`/`0x200`) is now clamped to 2000ms instead of accepting the full `uint16_t` range; the MLX90640/90641/90642 calibrated-chunk drivers now saturate instead of silently wrapping above ~327.67°C. Later still: a new command, `0x219`, relays the expansion slave bootloader's own `REG_VERIFY_FAIL_REASON` - a failed slave OTA update now reports which specific check failed (incomplete/CRC32/HMAC/HardwareID/rollback) instead of only a generic verify-fail status, the same detail this board's own `0x7F5` already provided for its own updates. Later still: `firmware_can_global_pre.c` now answers `0x7FB` (query CAN error counters) the same way it already answers `0x7F8` - see [`boot/CHANGELOG.md`](boot/CHANGELOG.md)'s own 0.1.3 entry for the full `0x7FB`/`0x7FC` protocol detail, since this same dual-answerable command is implemented on both sides. Later still: the CAN bus-off recovery block in the main loop now calls `HAL_CAN_AbortTxRequest()` on all 3 TX mailboxes before restarting the peripheral - previously, any message still queued in a mailbox at the moment of a bus fault stayed queued and could fire off once the bus recovered, carrying whatever stale telemetry/status payload it held from before the fault instead of a fresh one. Later still: the periodic F-RAM parameter-persistence save (`SavedState_MaybeSave()`, main loop) is now skipped for whichever loop iteration would otherwise write while an AOI strobe pulse (`aoi_strobe_active`) is lit - `FRAM_WriteBytes`'s own 50ms `HAL_I2C_Mem_Write` timeout on the F-RAM-unresponsive failure path could otherwise stall that iteration long enough to delay the strobe's own non-blocking off-timer check past its intended window, keeping the ring LED lit longer than the strobe period actually commanded. Deferred by up to one more 500ms tick at most; this data was never safety-relevant persistence to begin with (see `SavedState_Load()`'s own comment). Later still: `Update_StatusLED_SPI_DMA()` now captures `led_state_pixel`'s 3 color bytes under `__disable_irq()`/`__enable_irq()` before filling the SPI buffer - a CAN RX interrupt (`0x100` writes this same struct directly) landing mid-copy could previously hand the DMA transfer a torn mix of the old and new color for one frame; cosmetic only (status LED color, no actuator involved), but free to close given the existing SPI-busy check already prevents two transfers from overlapping. Later still: this binary's own filename convention changed - `build_firmware.sh`/`.bat` now name it `URTC_MAIN_FIRMWARE_v<MAJOR>.<MINOR>.<PATCH>.bin/.hex/.elf` (full PATCH included) instead of the old `URTC_V<MAJOR>.<MINOR>_F303CC.bin/.hex/.elf` (no PATCH) - part of unifying all 4 of this repo's own compiled-binary names onto ONE `<PREFIX>_v<MAJOR>.<MINOR>.<PATCH>` pattern, matching sibling repo HYDRA-UMC's own build_firmware.sh (see root [`CHANGELOG.md`](../../CHANGELOG.md) and `VERSION_CHECKLIST.txt` Track A3). Build-script/tooling change only, no application source change. The intermediate 0.1.9/0.2.0 builds used to verify the new naming logic on both `build_firmware.sh` and `build_firmware.bat` (real Windows `cmd`, not just read for syntax) before landing on this final version - one of them (`0.1.9` → `0.2.0`) an odometer carry, confirming that mechanism keeps working correctly with the new filename logic layered on top of it. Now at **0.2.1**, see **0.2.2**/**0.2.3** above for what's changed since. |
| **0.0** | Initial versioned release. Full support for all 12 tool profiles, hardware I2C2 OLED, per-tool CAN telemetry, and the communication/stall watchdogs described throughout the main README. Also includes the `0x110`/`0x111` active-tool query added for the Tester tool, the `11111`-jumper free tool configuration mechanism (`0x1A2`/`0x1A3` - see `docs/EEPROM.TXT` section 5), and peripheral type + device serial number reporting (`0x1A4`/`0x1A5` - see `docs/EEPROM.TXT` section 6), for telling multiple otherwise-identical boards apart on a shared CAN bus. Later fixes within this same version (no version bump, per this project's own rule that the firmware's version only changes on explicit request): the laser's PWM duty is now forced to 0 in software whenever the interlock isn't armed, instead of being generated purely from the power setpoint independent of interlock state; the bit-banged expansion I2C bus now actually runs at ~100kHz instead of the ~800kHz an incorrect delay loop had been producing; and a GPIO config struct wasn't being fully reset between pins, silently giving some digital outputs a faster edge rate than intended. |
