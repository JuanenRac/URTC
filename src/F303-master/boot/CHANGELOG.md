# Changelog - Bootloader (`src/F303-master/boot/`)

Versioned independently from the application firmware - flashing a new
bootloader doesn't imply a new application version and vice versa. The
firmware's own changelog lives at
[`../CHANGELOG.md`](../CHANGELOG.md).

| Version | Notes |
|---|---|
| **1.1.9** | Second verification build of the automated bootloader-version bump wired in for 1.1.8 (see that entry) - `build_firmware.bat` run again immediately after, confirming `bump_bootloader_version.py` correctly reads back its own just-written `1.1.8` and produces a second consecutive, correctly-incremented build (`1.1.8 -> 1.1.9`) with 0 warnings/0 failures across all 4 components. Source identical to 1.1.7 - no bootloader behavior change, version-mechanism verification only. |
| **1.1.8** | First bootloader binary built after wiring the ecosystem-wide versioning policy into the real build: `build_firmware.sh`/`.bat` now call `bump_bootloader_version.py` (new, repo root) as the first step of compiling this bootloader, bumping `BOOTLOADER_VERSION_PATCH` by 1 automatically before the compiler reads this header - carrying into `MINOR` (then `MAJOR`) with the same base-10 "odometer" rule a car's own odometer uses once `PATCH` would pass 9 (e.g. `1.1.9` is followed by `1.2.0`, never `1.1.10`). Application firmware (`FIRMWARE_VERSION_MAJOR`/`MINOR`) is explicitly untouched by this mechanism - it stays static, changed only by a human hand-editing it. Source identical to 1.1.7 otherwise - no bootloader behavior change, this bump is the versioning mechanism itself. |
| **1.1.7** | Fixed two defects found in a fresh line-by-line audit. `MX_I2C2_Init_Boot()` was enabling I2C1's peripheral clock (`__HAL_RCC_I2C1_CLK_ENABLE()`) while every actual register access used the I2C2 instance - the 1.0.8 fix corrected the GPIO alternate-function/instance mismatch but missed this clock-enable line, so I2C2 stayed unclocked and `oled_present_boot` always latched 0: this bootloader's OLED still never actually worked on real hardware after 1.0.8, just for a different reason than before. `HandleStartUpdate` (`0x7F1`) now validates the declared size/HardwareID into local variables before committing them to `update_total_size`/`update_declared_hw_id` - previously a malformed or out-of-order `0x7F1` arriving while a good update was already in progress would overwrite `update_total_size` with the rejected value while leaving `update_in_progress`/`update_bytes_received`/`page_buffer_fill`/`current_page_index` untouched, corrupting the state machine (a size that no longer matched what was actually erased for the in-flight transfer). |
| **1.1.6** | `HandleReadbackStart` (`0x7FE`) now validates `hardware_id`/`size` before trusting `meta.size`, same guard `ApplicationIsValid()` already applies - a torn-write metadata page (power loss mid-`Metadata_EraseAndWrite`, same scenario as the 1.1.2 fix) could leave `state==META_STATE_APP_VALID` with `hardware_id`/`size` still reading as erased flash, which the readback loop would then have copied unbounded past the end of real flash. Reachable by any node on the bus, no authentication required to trigger `0x7FE`. |
| **1.1.5** | New commands `0x7FE`/`0x7FF`: reads the main slot's own current contents back over CAN, unmodified, paced 2048 bytes per page with a host-sent acknowledgement between pages - the CAN equivalent of the Flasher's own "back up entire flash before erasing" SWD feature, for the same reason: a real copy of what's currently installed, worth having before deliberately overwriting it. Read-only, ignored while an update is already in progress. |
| **1.1.4** | New command `0x7FD`: authorizes the current update attempt to install a version older than what's already running, bypassing the anti-rollback check `0x7F4` otherwise always enforces - one-shot per attempt (reset at every fresh `0x7F1`, consumed the moment the anti-rollback check runs), for the genuine case of deliberately reverting to an older release rather than a permanent bypass. Still requires uploading the full older image through the normal `0x7F1`/`0x7F2`/`0x7F7`/`0x7F4` sequence - this only lifts the version-ordering check, not the transfer itself. |
| **1.1.3** | New command `0x7FB`/`0x7FC`: query the CAN peripheral's own TEC/REC (Transmit/Receive Error Counter), answered by whichever of the bootloader or application is currently running - same dual-answerable convention `0x7F8`/`0x7F9` already uses, read directly from the CAN controller's own `ESR` register rather than tracked in software. Lets a host tell a genuine bus problem (wiring, termination, bitrate mismatch) apart from an application/bootloader-side issue during a slow or stuck update. |
| **1.1.2** | `ApplicationIsValid()`'s `hardware_id`/`size` sanity check now runs before the `META_STATE_COPY_PENDING` resume branch reads `meta.size`, not after - a power loss during `Metadata_EraseAndWrite` between the `magic`+`state` halfwords committing and the `hardware_id`/`size` halfwords committing left `state==META_STATE_COPY_PENDING` with `size` still reading as erased flash, which `Flash_CopyRegion` would then have acted on unbounded. `HandleData`'s and `HandleEndUpdate`'s own page-flush-failure paths now clear `update_in_progress` alongside `update_failed`, matching every other error path in this same state machine. |
| **1.1.1** | `HandleVersionQuery` now actually returns an all-zero HardwareID when no valid firmware is installed, matching what its own comment already promised - it had been returning this bootloader's own compiled-in HardwareID instead, which broke `URTC Flasher`'s own `hardware_id==0` check for showing "no valid firmware currently installed". Later, within this same version: the monolithic single-file build was retired, same reorganization as the firmware's own 1.1 entry - `bootloader_main.c` and the rest of what lived in `boot/partitioned/` moved up to `src/F303-master/boot/` directly. No functional change. |
| **1.1.0** | The entry point file is now named `bootloader_main.c` (matches the firmware's own `STM32F303CC_main.c` convention for its equivalent file). |
| **1.0.9** | The jump-to-application stack pointer check no longer accepts a value sitting exactly at the base of either RAM region, which would have faulted on the very first `PUSH` after handoff - both bounds now require a small margin instead. The version-query response (`0x7F9`) now retries on a busy CAN mailbox the same way `0x7FA` already did, instead of silently dropping the whole reply. Added an explicit I2C2 peripheral teardown and a memory barrier before the post-write flash verification read, both matching safety patterns already used elsewhere in this same handoff path. The signing key constant is now defined once and referenced from every module that needs it, instead of a private copy compiled into each one. |
| **1.0.8** | Fixed the OLED's I2C peripheral: PA9/PA10 with AF4 is I2C2, not I2C1 (confirmed against ST's own datasheet) - the same mistake already found and fixed in the application firmware, but never checked here until now, meaning this bootloader's OLED (the "UPDATING"/progress/error screens) would never have actually worked on real hardware. Also: hardware ID now reports the compiled-in value instead of 0 on a blank chip, an immediate first heartbeat instead of waiting a full second, and general cleanup (dual-CAN filter-bank setting that had no effect on this single-CAN chip, a lowercase-to-uppercase font fallback, a wider I2C timeout during the boot-time OLED wake-up window). |
| **1.0.7** | Batches the CRC32 calculation once per received CAN frame instead of once per byte (an 8x reduction in call count across a full transfer). A defensive `__disable_irq()` before the vector-table/stack-pointer handoff to the application. Explicit state cleanup on an erase failure during a new update attempt. 1px of inter-character spacing added to the boot-screen font renderer, which previously ran letters together into a hard-to-read block. |
| **1.0.6** | The bootloader's own version-query response (`0x7FA`) now retries if the CAN mailbox was still busy from the `0x7F9` frame sent right before it, instead of silently dropping. |
| **1.0.5** | Extended the CAN mailbox retry window from 5ms to 50ms, giving genuine bus congestion far more room to clear before a status frame gets dropped (still a small fraction of the ~800ms watchdog window). Added a periodic watchdog refresh inside the flash program/verify loops themselves, not just once per page, as extra margin against unexpected timing delays. Stack pointer bounds now reference CMSIS's own base-address constants instead of hardcoded literals. |
| **1.0.3** | Corrected the jump-to-application stack pointer validation: this chip has two real RAM regions a legitimate stack pointer could sit in (40KB standard SRAM at `0x20000000`, and a separate 8KB CCM - Core-Coupled Memory - region at `0x10000000`, confirmed against ST's own datasheet), and the check previously only accepted the first. |
| **1.0.2** | Fixed an off-by-one stack buffer overflow in the OLED status-message renderer (not triggered by any of this bootloader's own current status messages, but a real defect for any future one long enough to reach the affected column). Added frame-type validation (rejects RTR/extended-ID frames) before any CAN command is acted on, so a Remote Transmission Request can't be mistaken for a real data frame carrying stale bytes. Forces GPIO to a safe, disconnected state and clears any latched-pending SysTick interrupt immediately before jumping to the application, on top of the peripheral teardown already done there. |
| **1.0.1** | Anti-rollback protection (a validly-signed image older than what's installed is rejected - `0x05` verify-fail reason `0x05`), stricter jump-to-application checks (stack alignment, Thumb-state and address-range validation on the reset vector), a corrected RAM bound matching this chip's actual 40KB of contiguous SRAM, and general hardening around the OLED/CAN/flash timing paths. |
| **1.0.0** | Initial versioned release. HMAC-SHA256 signed OTA updates, golden-image A/B backup slot, and `0x7FA` - the bootloader's own version, reported alongside `0x7F9` (the installed application's version) whenever the bootloader itself answers a version query. |
