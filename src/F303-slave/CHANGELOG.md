# Changelog - Expansion Slave Application (`src/F303-slave/`, STM32F303CBT6)

Versioned entirely independently of the main board's own firmware/
bootloader - a separate chip, on a separate board, in a separate
source tree. The slave's own bootloader changelog lives at
[`boot/CHANGELOG.md`](boot/CHANGELOG.md); the main board's firmware
changelog lives at
[`../F303-master/CHANGELOG.md`](../F303-master/CHANGELOG.md).

| Version | Notes |
|---|---|
| **0.1.0** | Naming-convention-unification build (build script change only, no application source change; odometer carry from `0.0.9`, patch past 9 resets to 0, minor +1): `build_firmware.sh`/`.bat` now name this binary `URTC_SLAVE_FIRMWARE_v<MAJOR>.<MINOR>.<PATCH>.bin/.hex/.elf` (e.g. `URTC_SLAVE_FIRMWARE_v0.1.0.bin`) instead of the old unversioned `URTC_SLAVE_APP.bin/.hex/.elf` - same `<PREFIX>_v<MAJOR>.<MINOR>.<PATCH>` convention now shared by all 4 of this repo's own components, matching sibling repo HYDRA-UMC's own build_firmware.sh (see root [`CHANGELOG.md`](../CHANGELOG.md)). `generate_manifest.py` was updated to glob for this new pattern rather than a hardcoded name. Old-named binaries from before this bump, and the intermediate 0.0.8/0.0.9 builds used to verify the new naming logic on both `build_firmware.sh` and `build_firmware.bat` before landing on this final 0.1.0, moved to `the project archive` per this project's own no-permanent-delete convention, not deleted outright. |
| **0.0** | Initial release. I2C1 link-bus protocol (this chip as slave) to the main board; I2C2 local sensor bus (this chip as master) driving an ADS1115 16-bit ADC and an MLX9064x thermal camera, built on Melexis's own official library rather than a hand-rolled register map; 4-channel local PWM generation (TIM1) for tools needing sub-millisecond pulse timing generated at the tool head itself. Later, still within this same version (no version bump, per this project's own rule that the slave's own application version only changes on explicit request): MLX90641 and MLX90642 support added alongside the original MLX90640 support - 2 genuinely separate Melexis libraries (`melexis_mlx90641/`, `melexis_mlx90642/`), not variants of the first one; MLX90641's own upstream form is this project's own first C++ code, built into an otherwise all-C firmware, while MLX90642 turned out genuinely simpler than the other two (no host-side calibration math at all - it reports temperature already calculated). A new register (`REG_MLX_SENSOR_VARIANT`) and matching main-board CAN command (`0x1A6`/`0x1A7`) let the host say which of the 3 MLX9064x family members is actually populated, relayed to this chip at boot since it has no persistent storage of its own. Later still: `FIRMWARE_VERSION_PATCH` added to `slave_common.h` as part of rolling out the ecosystem-wide incremental versioning policy (this component was previously `MAJOR.MINOR` only, static in practice) - a mechanism change, not a behavior change. Now at **0.0.7**: builds 0.0.1-0.0.7 beyond that mechanism change are build-verification bumps via `bump_version.py`, with no functional change to this application's own logic found in today's full-ecosystem audit. |
