# Changelog - Expansion Slave Bootloader (`src/F303-slave/boot/`, STM32F303CBT6)

Versioned entirely independently of the main board's own firmware/
bootloader - a separate chip, on a separate board, in a separate
source tree. The slave's own application changelog lives at
[`../CHANGELOG.md`](../CHANGELOG.md); the main board's bootloader
changelog lives at
[`../../F303-master/boot/CHANGELOG.md`](../../F303-master/boot/CHANGELOG.md).

| Version | Notes |
|---|---|
| **0.1.3** | Naming-convention-unification build (build script change only, no bootloader source change): `build_firmware.sh`/`.bat` now name this binary `URTC_SLAVE_BOOTLOADER_v<MAJOR>.<MINOR>.<PATCH>.bin/.hex/.elf` (e.g. `URTC_SLAVE_BOOTLOADER_v0.1.3.bin`) instead of the old unversioned `URTC_SLAVE_BOOTLOADER.bin/.hex/.elf` - same `<PREFIX>_v<MAJOR>.<MINOR>.<PATCH>` convention now shared by all 4 of this repo's own components, matching sibling repo HYDRA-UMC's own build_firmware.sh (see root [`CHANGELOG.md`](../../../CHANGELOG.md)). `generate_manifest.py` was updated to glob for this new pattern rather than a hardcoded name. Old-named binaries from before this bump, and the intermediate 0.1.1/0.1.2 builds used to verify the new naming logic on both `build_firmware.sh` and `build_firmware.bat` before landing on this final 0.1.3, moved to `the project archive` per this project's own no-permanent-delete convention, not deleted outright. |
| **0.1.0** | Odometer carry from `0.0.9` (patch past 9 resets to 0, minor +1). Builds 0.0.4-0.1.0 are verification/mechanism-check bumps, same "no bootloader behavior change" pattern already documented by 0.0.2/0.0.3 below - no defects found in this bootloader during today's full-ecosystem audit. |
| **0.0.3** | Second verification build of the automated bootloader-version bump wired in for 0.0.2 (see that entry) - `build_firmware.bat` run again immediately after, confirming `bump_bootloader_version.py` correctly reads back its own just-written `0.0.2` and produces a second consecutive, correctly-incremented build (`0.0.2 -> 0.0.3`) with 0 warnings/0 failures across all 4 components. Source identical to 0.0.1 - no bootloader behavior change, version-mechanism verification only. |
| **0.0.2** | First bootloader binary built after wiring the ecosystem-wide versioning policy into the real build - same mechanism, same commit, as the main board bootloader's own 0.1.8 entry (see [`../../F303-master/boot/CHANGELOG.md`](../../F303-master/boot/CHANGELOG.md)): `build_firmware.sh`/`.bat` now call `bump_bootloader_version.py` as the first step of compiling THIS bootloader too, bumping `BOOTLOADER_VERSION_PATCH` automatically before compiling, with the same odometer-carry rule into `MINOR`/`MAJOR`. The slave application (`FIRMWARE_VERSION_MAJOR`/`MINOR` in `slave_common.h`) stays static, untouched by this mechanism. Source identical to 0.0.1 otherwise - no bootloader behavior change. |
| **0.0.1** | Same `hardware_id`/`size` validation-ordering fix as the main board's own bootloader v0.1.2 (see [`../../F303-master/boot/CHANGELOG.md`](../../F303-master/boot/CHANGELOG.md)) applied here too - inherited from the same original design, not introduced by the port. A 10s update-inactivity timeout now reverts a stalled transfer back to `STATUS_LISTENING`, matching the main board's own bootloader. `VERIFY_FAIL_REASON_*` (already defined, previously never assigned to anything) is now set alongside `STATUS_VERIFY_FAIL` and exposed through a new register, `REG_VERIFY_FAIL_REASON` (`0x07`), so a host can tell which specific check failed instead of only seeing the generic `STATUS_VERIFY_FAIL`. `update_progress_percent` now resets to its documented `0xFF` ("not updating") sentinel on an erase failure during `HandleStartUpdate`, instead of holding whatever percentage a prior update left behind. `HandleData`'s and `HandleEndUpdate`'s own page-flush-failure paths now clear `update_in_progress` alongside `update_failed`. |
| **0.0.0** | Initial release. Same A/B golden-image update model as the main board's own bootloader, scaled to this chip's 128KB flash, relayed over the I2C link rather than CAN directly - this chip has no CAN peripheral of its own. |
