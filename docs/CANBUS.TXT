CRITICAL RECONSTRUCTION NOTE: All multi-byte fields are transmitted in
BIG-ENDIAN format (Most Significant Byte [MSB] first on the wire). The
STM32F303 firmware must unpack them strictly respecting this order.
The two companion links that do not travel on this bus follow the same order: the rack serial
frame version 2 (temperature of the pre-heat command) and the sensor frame version 2 of the vision
head (timestamp and thermal reading) are big-endian; version 1 of both was little-endian and is
refused as an unsupported version. Their vectors are in the shared conformance repository.

-----------------------------------------------------------------------------
1. MAXIMUM-PRIORITY COMMANDS (Critical Events / Interrupts)
-----------------------------------------------------------------------------
ID: 0x095 [URTC Tool Head -> Master] (INSTANT SEND VIA EXTI INTERRUPT)
DLC: 1 byte
Data:
  - txData[0]: Collision event / surface contact register
               0x01 = IMPACT DETECTED! (Edge on PB3)
  Note: Critically low ID so it always wins hardware arbitration on the CAN
        bus. This frame bypasses schedulers entirely; it is injected with
        absolute priority straight from the EXTI3 interrupt callback (PB3
        pin) to avoid probe damage during high-speed scanning.

-----------------------------------------------------------------------------
2. GLOBAL COMMANDS (Valid for any active tool)
-----------------------------------------------------------------------------
ID: 0x100 [Master -> URTC Tool Head]
DLC: 8 bytes
Data:
  - rxData[0]: Red LED intensity (R) - Status LED color, CONN_LED1 (0-255)
  - rxData[1]: Green LED intensity (G) - Status LED color, CONN_LED1 (0-255)
  - rxData[2]: Blue LED intensity (B) - Status LED color, CONN_LED1 (0-255)
    * CONN_LED1 has an automatic default (see below) - this
      message is an OVERRIDE, not the only way its color gets set. The
      override holds for 10s from the last 0x100 received (each new 0x100
      refreshes that window), then falls back to automatic. A hardware
      fault always takes over regardless of any active override.
  - rxData[3]: Display and night-mode control
               0x00 = Standard mode (OLED at normal brightness / High contrast 0xCF)
               0x01 = Night mode active (OLED low-power / Minimum contrast 0x0F)
               0x0F = Display in Standby / Display OFF (anti-burn-in protection)
  - rxData[4]: Red intensity (R) - Ring LED color, CONN_LED2 (0-255)
  - rxData[5]: Green intensity (G) - Ring LED color, CONN_LED2 (0-255)
  - rxData[6]: Blue intensity (B) - Ring LED color, CONN_LED2 (0-255)
  - rxData[7]: Ring on/off
               0x00 = Ring off
               0x01 = Ring on, solid, at the rxData[4:6] color
  Note: CONN_LED1 (status LED) automatic scheme, applied whenever no host
        override from this message is currently held: red if a hardware
        fault is active (system_error_flag, highest priority, always wins),
        blue if a CAN frame of any ID arrived within the last 1.5s ("actively
        functioning"), green otherwise ("idle, waiting for commands"). The
        local diagnostic LED (PA15) is separate and unrelated to this -
        5Hz blink while the main loop is alive, solid on for a fault.
  Note: In TOOL_AOI_INSPECTION mode, rxData[7] (ring on/off) is ignored - the
        ring there is driven by 0x150 (off/strobe/continuous) instead, so it
        can flash in sync rather than just switch on/off. rxData[4:6] still
        updates the stored color even in AOI mode, so a color change takes
        effect immediately if 0x150's mode is already set to continuous.

ID: 0x110 [Master -> URTC Tool Head]
Query active tool + quick state
DLC: any (payload ignored)
Data: none needed
Effect: answers with 0x111. Read-only, no side effects - answered even
        while a critical error is declared, unlike most commands, since
        this is exactly the kind of diagnostic that matters most when
        something's already wrong. A host has no other way to learn which
        of the 25 tool profiles a board is jumpered for without this,
        short of probing which tool-specific IDs happen to get a
        response - which takes time and can't distinguish "no response
        yet" from "wrong tool for this command".

ID: 0x111 [URTC Tool Head -> Master, answers 0x110]
Active tool + quick state response
DLC: 6 bytes (firmware 0.3.2+; older firmware answers with the first 4 -
     a host must treat missing bytes 4-5 as "not reported", not as 0)
Data:
  - txData[0]: Active tool (matches the ToolMode_t enum in
               firmware_common.h): 0=Soldering Iron, 1=Paste Dispenser,
               2=Liquid Dispenser, 3=Screwdriver, 4=Vacuum Pickup,
               5=Drill, 6=Gripper Gimbal, 7=Gripper NEMA, 8=AOI
               Inspection, 9=Laser Engraver, 10=3D Printer, 11=Scan
               Probe, 12=SMT Pick & Place, 13=Electromagnet, 14=Spot
               Welder, 15=Conformal Coating, 16=Vacuum Gripper (LG),
               17=Flying Probe, 18=UV Curing, 19=Hot Air Rework,
               20=Press-Fit Inserter, 21=Crimping Actuator,
               22=Thermal Inspection, 23=Paste Jetting, 24=Ultrasonic
               Welder - see docs/TOOLS.TXT for what each one actually
               does. 25 (TOOL_INVALID) = no tool assigned to this
               jumper setting (see firmware_common.h's own
               TOOL_INVALID note); 0x19-0x1E on the ID-jumper matrix
               itself resolve here too, since those 6 raw jumper
               readings are also currently unassigned - see
               ECOVIA.TXT's own addressing table for the full picture.
               This is the already-resolved value, not the raw ID-jumper
               reading - a board whose jumpers read 0x1F (free
               configuration, see EEPROM.TXT section 5) reports whichever
               real tool number the F-RAM resolved it to here, or still
               25 if that register was never set. 0x1A3 reports the raw
               jumper reading separately, for telling "jumpers read
               something other than 0x1F" apart from "jumpers read 0x1F
               but unconfigured."
  - txData[1]: system_error_flag (0x01 = a critical fault is currently declared)
  - txData[2]: can_bus_error_flag (0x01 = a CAN bus fault was seen)
  - txData[3]: boot_sequence_active (0x01 = still inside the ~5s boot
               splash window - movement commands are deferred until this clears)
  - txData[4]: thermal_fault_code - WHY the heater was cut by the thermal
               runaway guard (thermal_guard.c), 0 if it never was:
                 0 = none
                 1 = MAXTEMP (measured temperature above the hard ceiling:
                     449 C T12/hot air, 310 C 3D hotend)
                 2 = HEATING_NO_RISE (heater on, far below target, but the
                     temperature did not rise - loose sensor/tip, dead heater)
                 3 = DROPPED_AT_TARGET (target reached, then sagged far
                     below it with the heater on - sensor fell out)
               A non-zero code always comes with txData[1] = 0x01. The
               heater stays off until the board is reset - see
               firmware_control_thermal.c.
  - txData[5]: last_reset_cause - RCC reset flags latched at boot:
               bit0 IWDG (the hardware watchdog fired: the main loop hung),
               bit1 WWDG, bit2 software reset (also what the bootloader's
               jump/update path produces), bit3 power-on/brown-out,
               bit4 NRST pin, bit5 low-power, bit6 option-byte load.

ID: 0x180 [Master -> URTC Tool Head]
Expansion SPI passthrough (CONN_EXPANSION)
DLC: 2-8
Data:
  - rxData[0]: N - how many of the following bytes to clock over the
               expansion connector's SPI bus (1-7; a value >7 or larger
               than what DLC actually carries is silently clamped down to
               whichever is smaller, rather than treated as an error)
  - rxData[1..N]: the N bytes to send, in order
Effect: asserts EXP_SPI_CS_PIN low, clocks all N bytes (SPI Mode 3 -
        confirmed against the TMC5160 datasheet's own SPI Interface
        section, not assumed), releases EXP_SPI_CS_PIN high, answers with
        0x181. Blocked while a critical error is declared, same as every
        actuation command other than 0x100 - this drives signals to an
        external device, unlike the purely-diagnostic 0x110/0x111 pair.
        Generic byte transport: this firmware doesn't interpret the
        TMC5160's (or any other chip's) specific register protocol at
        all - that's left to whatever's on the master side of this
        connection, since the actual expansion board isn't finalized yet.
        Firmware-side implementation: ExpansionSPI_TransferByte() in
        firmware_expansion_spi.c.

ID: 0x181 [URTC Tool Head -> Master, answers 0x180]
Expansion SPI passthrough response
DLC: 2-8
Data:
  - txData[0]: N, matching the request
  - txData[1..N]: the N bytes read back on MISO during that same
               transfer - SPI is inherently full-duplex, so every byte
               sent is also a byte received, whether or not the caller
               cares about the response for a particular byte position
               (e.g. the address byte of a TMC5160 write access reads
               back a don't-care value, per that chip's own datasheet)

ID: 0x182 [Master -> URTC Tool Head]
Query TMC_DIAG0 level
DLC: any (payload ignored)
Data: none needed
Effect: answers with 0x183 - the current level of TMC_DIAG0 (PC15), a
        combined stall/fault diagnostic line: the onboard TMC2209's own
        DIAG output and whatever driver populates CONN_EXPANSION are
        diode-ORed together onto this single pin (D4, a common-cathode
        dual diode), so this one query covers both. Simple polled read,
        not an interrupt-driven push - a real hardware EXTI on this pin
        (matching the scan probe's own pattern on PB3) is a natural
        future addition once real-world latency requirements are clear,
        not built speculatively ahead of that.

ID: 0x183 [URTC Tool Head -> Master, answers 0x182]
TMC_DIAG0 level response
DLC: 1 byte
Data:
  - txData[0]: 1 if the line reads high, 0 if low. Active-HIGH: either
               driver's DIAG going high pulls the shared node high
               through its own diode, so 1 means a stall/error
               condition on the onboard driver, the expansion driver,
               or both - this reading alone can't distinguish which.
               No internal pull-up on this pin - an external pull-down
               (10K) on the board itself holds the line at a stable,
               known 0 when neither driver is asserting, so a board
               with nothing populated on the expansion connector still
               reads a clean 0, not a floating value. A TMC5160
               populating the expansion connector needs its own
               GCONF.diag0_int_pushpull bit set to 1 (push-pull/
               active-high) for its side of this to work correctly -
               left at its power-on default (open-drain/active-low),
               a stall on that side won't register here at all. See
               EXPANSION.TXT for the full reasoning.

ID: 0x190 [Master -> URTC Tool Head]
Query recovered persisted state
DLC: any (payload ignored)
Data: none needed
Effect: answers with 0x191 - whatever was loaded from the FM24CL64B
        persistence F-RAM at boot (see firmware_persistence.c's own SavedState_Load).
        Read-only, no side effects, and deliberately does NOT itself
        re-apply anything to a live setpoint - see the note on 0x191
        below for why. Answered even during a declared critical error,
        same reasoning as 0x110/0x111: read-only diagnostics stay
        available exactly when something's already gone wrong.

ID: 0x191 [URTC Tool Head -> Master, answers 0x190]
Recovered persisted state response
DLC: 8 bytes
Data:
  - txData[0]: 1 if a valid saved state was found and loaded, 0 if not
               (uninitialized F-RAM, checksum mismatch from a
               corrupted/interrupted save, or the chip didn't respond
               at all - all three look the same from here: nothing
               trustworthy to report)
  - txData[1]: which tool profile this saved state was recorded under
               (matches the ToolMode_t values - see 0x111)
  - txData[2]: 1 if a critical error was active at the moment of the
               last save (i.e. the board may have gone down mid-fault,
               not just mid-power-loss)
  - txData[3:4]: temperature setpoint at the last save (soldering iron
               or 3D-printer nozzle, whichever the recorded tool was -
               they share one field since only one is ever relevant for
               a given board's fixed active_tool)
  - txData[5]: speed/power setpoint at the last save (drill speed or
               laser power, same one-or-the-other reasoning)
  - txData[6]: 1 if the drill was set to reverse, or the laser interlock
               was armed, whichever was relevant (0 otherwise)
  - txData[7]: 3D-printer layer fan power at the last save
Notes: this is a compact summary, not the full ~26-byte record kept in
       RAM (recovered_state, owned by firmware_persistence.c) - a single CAN frame can't
       carry that much. Nothing here gets applied to a live setpoint
       automatically on boot, by design: a heater, the laser, or a motor
       quietly re-arming itself the instant the board powers back up
       would undermine every communication watchdog documented
       elsewhere in this file. This tells a host what the board was
       doing before it went down; deliberately re-commanding the same
       setpoint (or a different one) afterward is the host's decision to
       make, not something this board does on its own initiative.

ID: 0x192 [Master -> URTC Tool Head]
Erase recovered persisted state
DLC: 4 bytes, magic payload E3 A5 E0 FF
Data:
  - rxData[0..3]: must be exactly E3 A5 E0 FF - any other payload (or any
               other DLC) is silently ignored. Same reasoning as 0x7F0's
               own magic trigger: a corrupted or malformed frame landing
               on this ID by chance shouldn't be able to wipe a real
               saved record.
Effect: overwrites the entire saved-state region of the F-RAM with
        0xFF (an arbitrary but definite pattern, guaranteed to fail the
        magic/checksum check - unlike Flash/EEPROM, F-RAM has no
        erase-before-write step, so 0xFF has no special hardware
        significance here beyond being a value this firmware will
        always recognize as invalid), clears recovered_state
        and had_valid_recovered_state in RAM immediately (not just on
        the next boot), and answers with 0x191 reporting
        had_valid_recovered_state=0 to confirm. Unlike 0x110/0x190,
        this is NOT answered during a declared critical error - it's a
        destructive write, even though not physically hazardous the way
        an actuator command would be, so it stays behind the same
        error-gate as everything else that isn't a pure read-only
        diagnostic.

ID: 0x1A0 [Master -> URTC Tool Head]
Set expansion board type
DLC: 1+ bytes (only byte[0] used)
Data:
  - rxData[0]: 0-6, see EXPANSION.TXT for what each value means. Any
               other value is silently ignored (not written, not
               acknowledged as an error - just no change).
Effect: sets which of the 7 possible CONN_EXPANSION configurations is
        physically installed - there's no electrical way to sense this,
        so it has to be told rather than detected. Persists across power
        cycles the same way any other saved setting does (via the normal
        F-RAM change-detection, not forced immediately). Also answers
        with 0x1A1, same as directly querying it. Answered even during a
        declared critical error, same reasoning as 0x110/0x190: this is
        configuration, not an actuation command.

ID: 0x1A1 [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x1A0]
Query/response: current expansion board type
DLC: any as a query (payload ignored) | 1 byte as a response
Data:
  - txData[0]: the currently-set value, 0-6 (see EXPANSION.TXT)

ID: 0x1AA [Master -> URTC Tool Head]
Query lifetime thermal counters
DLC: any
Effect: answers with 0x1AB. Read-only, answered whatever the active tool or
        error state (like 0x110).

ID: 0x1AB [URTC Tool Head -> Master, answers 0x1AA]
Lifetime thermal counters (firmware 0.3.3+, thermal_stats.h)
DLC: 8 bytes
Data:
  - txData[0..1]: thermal runaway faults ever latched (BE16, saturates)
  - txData[2..5]: total time the heater output has been ON, in seconds
                  (BE32, saturates) - T12/hot air and 3D hotend share the
                  same heater output
  - txData[6]:    code of the most recent fault (same values as 0x111
                  byte 4), 0 = never
  - txData[7]:    0x01 = kept in F-RAM (THERMAL_STATS_FRAM_ADDR 192, its
                  own CRC-8 record, saved at most once a minute and at
                  once on a fault), 0x00 = F-RAM missing - RAM-only since boot

ID: 0x1AC [Master -> URTC Tool Head]
Switch the multinode extension on or off (firmware 0.3.8+, firmware_multinode.c)
DLC: 6 bytes
Data:
  - rxData[0..3]: magic payload 0x4D 0x4E 0x4F 0x44 (ASCII 'MNOD')
  - rxData[4]:    0 = off, 1 = on (any other value: the frame is ignored)
  - rxData[5]:    instance number announced in NODE_INFO (0 for the first
                  head of a tool type)
Effect: stores the setting in its own F-RAM record (address 960, EEPROM.TXT
        section 8) and answers with 0x1AD. The setting acts after the NEXT
        power-up, never in the middle of a job. The default is OFF: a board
        that was never written, with an erased or damaged record, behaves
        exactly as a single head, as in earlier releases. Blocked during a
        critical error. While the extension is on, this frame is obeyed only
        by the selected node (see the appendix at the end of this file).
        Like every persistent CAN setting it is protected by the magic
        payload against corrupted frames, not by authentication (see
        CAN_THREAT_MODEL.TXT): keep the bus closed.

ID: 0x1AD [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x1AC]
Query/response: the multinode switch
DLC: any as a query (payload ignored) | 4 bytes as a response
Data:
  - txData[0]: stored in F-RAM (0 or 1)
  - txData[1]: in force now (0 or 1); differs from txData[0] until the
               next power-up
  - txData[2]: instance number
  - txData[3]: node address read from the ID jumpers (0-31)

ID: 0x1AE [Master -> URTC Tool Head]
Switch the optional firmware features on or off (fw_features.c, firmware_features.c)
DLC: 5 bytes
Data:
  - rxData[0..3]: magic payload 0x46 0x45 0x41 0x54 (ASCII 'FEAT')
  - rxData[4]:    bit mask of the features to have ON (any bit outside 0x0F:
                  the frame is ignored)
                  0x01 = stepper ramps (trapezoid and S-curve, see 0x120)
                  0x02 = health frame (0x1B8)
                  0x04 = oscillator trim against the CAN bit time
                  0x08 = heater PID with relay autotune (0x1B9 / 0x1BA)
Effect: stores the mask in its own F-RAM record (address 976, EEPROM.TXT
        section 8) and answers with 0x1AF. The setting acts after the NEXT
        power-up, never in the middle of a job. Every feature is OFF by
        default: a board that was never written, with an erased or damaged
        record, behaves exactly as in earlier releases. Blocked during a
        critical error. Like every persistent CAN setting it is protected by
        the magic payload against corrupted frames, not by authentication
        (see CAN_THREAT_MODEL.TXT): keep the bus closed.
        Not yet tried on a board: the logic is tested on the host; the step
        timer, the analogue channels of the health frame and the oscillator
        measurement need a bench (see CHANGELOG.md).

ID: 0x1AF [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x1AE]
Query/response: the optional firmware features
DLC: any as a query (payload ignored) | 3 bytes as a response
Data:
  - txData[0]: stored in F-RAM (bit mask)
  - txData[1]: in force now (bit mask); differs from txData[0] until the
               next power-up
  - txData[2]: supported by this firmware (0x0F)

ID: 0x1B8 [URTC Tool Head -> Master]
Health frame of the board (only while feature 0x02 runs; once a second)
DLC: 8 bytes
Data:
  - txData[0]: transmit error counter of the CAN peripheral (TEC)
  - txData[1]: receive error counter (REC)
  - txData[2]: bus-off events since power-up (saturates at 255)
  - txData[3]: HSI trim value in force (16 = factory value)
  - txData[4]: longest main-loop pass since the last frame, ms (saturates at 255)
  - txData[5]: chip temperature + 40 in degrees C (0 = not available)
  - txData[6..7]: analogue supply in millivolts, big-endian (0 = not available)
  Note: sent whichever tool is active; a host treats 0 in the temperature and
        the supply as not reported.

ID: 0x1B9 [Master -> URTC Tool Head]
Heater PID: gains and relay autotune (only while feature 0x08 runs)
DLC: 7 bytes
Data:
  - rxData[0..1]: Kp x 100 [BIG-ENDIAN]
  - rxData[2..3]: Ki x 100 (per second)
  - rxData[4..5]: Kd x 100 (seconds)
  - rxData[6]:    0 = store the gains of this frame (each at most 600.00),
                  1 = start the relay autotune around the current setpoint
                      (soldering iron or hot air tool, no error, setpoint
                      100..445 C),
                  2 = abort a running autotune, 3 = change nothing
Effect: the gains are kept in the F-RAM (address 992) when they are set or
        when an autotune ends. The thermal guards and the absolute ceiling
        judge the PID output exactly as they judge the bang-bang one. The
        hotend of the 3D printer keeps its bang-bang control. Answered with 0x1BA.

ID: 0x1BA [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x1B9]
Query/response: the heater PID
DLC: any as a query (payload ignored) | 8 bytes as a response
Data:
  - txData[0..1]: Kp x 100 in force
  - txData[2..3]: Ki x 100
  - txData[4..5]: Kd x 100
  - txData[6]:    0 = feature off, 1 = running, 2 = autotuning,
                  3 = autotune done (gains stored), 4 = autotune failed
  - txData[7]:    heater output of the last control cycle, percent

ID: 0x1A2 [Master -> URTC Tool Head]
Set free tool configuration
DLC: 1+ bytes (only byte[0] used)
Data:
  - rxData[0]: 0-25. 0 = no tool selected, 1-25 = one of the 25
               currently supported tool profiles (stored/sent as id+1,
               not the raw 0-24 tool ID - see EEPROM.TXT section 5).
               Any other value is silently ignored (not written, not
               acknowledged as an error - just no change).
Effect: sets which tool profile a board whose ID jumpers read 0x1F
        (11111b, all 5 installed) should use - see EEPROM.TXT section 5
        for the full mechanism. Has no effect at all on a board whose
        jumpers read anything else; Identify_PhysicalTool() only
        consults this register when the jumper reading is specifically
        0x1F, and only once, at boot. Persists across power cycles the
        same way any other saved setting does (via the normal F-RAM
        change-detection, not forced immediately) - takes effect on the
        NEXT power cycle, not immediately, same as physically changing
        the ID jumpers themselves would. Also answers with 0x1A3, same
        as directly querying it. Answered even during a declared
        critical error, same reasoning as 0x110/0x190/0x1A0: this is
        configuration, not an actuation command.

ID: 0x1A3 [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x1A2]
Query/response: raw ID-jumper reading and current free tool configuration
DLC: any as a query (payload ignored) | 2 bytes as a response
Data:
  - txData[0]: the raw 5-bit ID-jumper reading (0-31) from this board's
               last boot - NOT active_tool, the unresolved reading
               itself. Lets a reader tell "jumpers read something other
               than 0x1F" (this register isn't even being consulted)
               apart from "jumpers read 0x1F but nothing's configured
               yet" (txData[1]==0 below), which txData[1] alone
               couldn't distinguish.
  - txData[1]: the currently-set free_tool_selection value, 0-25 (see
               0x1A2 above)

ID: 0x1A4 [Master -> URTC Tool Head]
Set device serial number
DLC: 1+ bytes (only byte[0] used)
Data:
  - rxData[0]: 0-255, any value accepted (no validation - the full
               uint8_t range is a valid serial number by design)
Effect: sets this board's device_serial_number, purely a host-assigned
        label for telling multiple otherwise-identical URTC boards apart
        on a shared CAN bus - see EEPROM.TXT section 6. This firmware
        never reads its own serial number for any decision; nothing
        else in this protocol changes behavior based on it. Persists
        across power cycles the same way free_tool_selection does (via
        the normal F-RAM change-detection, not forced immediately).
        Also answers with 0x1A5, same as directly querying it. Answered
        even during a declared critical error, same reasoning as
        0x110/0x190/0x1A0/0x1A2: this is configuration, not an
        actuation command.

ID: 0x1A5 [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x1A4]
Query/response: peripheral type and device serial number
DLC: any as a query (payload ignored) | 2 bytes as a response
Data:
  - txData[0]: peripheral type - always 0x03 for URTC firmware, a fixed
               identity constant (URTC_PERIPHERAL_TYPE in the source),
               never written, never persisted. 0x04-0x05 are reserved
               for an expansion board's own firmware to report about
               itself - not something this codebase answers on an
               expansion board's behalf (different chip, different
               firmware entirely - see EEPROM.TXT section 6).
  - txData[1]: the currently-set device_serial_number value, 0-255 (see
               0x1A4 above)

ID: 0x1A6 [Master -> URTC Tool Head]
Set MLX9064x sensor variant
DLC: 1+ bytes (only byte[0] used)
Data:
  - rxData[0]: 0=none installed, 1=MLX90640, 2=MLX90641, 3=MLX90642
               (MLX_VARIANT_* in the source) - which of the 3 MLX9064x
               family members is actually populated on either this
               board's own Basic+MLX9064x expansion board (direct
               connection, expansion_board_type==6, see EXPANSION.TXT)
               or an Advanced expansion board's own local sensor bus,
               or that none is populated at all (0, the safe default -
               deliberately NOT "assume MLX90640", a real MLX90640
               needs this set explicitly). Values above 3 are rejected
               (no change made, still answers with the unchanged
               current value).
Effect: sets this board's own mlx_sensor_variant, used two ways
        depending on which expansion board is actually configured
        (expansion_board_type, 0x1A0/0x1A1):
          - expansion_board_type==6 (Basic+MLX9064x, direct): this
            board's own thermal-inspection CAN handler (0x250-0x255,
            see section further below) reads mlx_sensor_variant
            directly to decide which sensor library to call - or
            answers nothing at all (0x250/0x252/0x254) or
            MLX_CAPTURE_ERROR (0x251) if this is still 0 (none
            configured).
          - expansion_board_type==3 or 4 (either Advanced variant): the
            new value is also relayed live, over the same I2C bridge
            used for every other advanced-board register access, to the
            expansion slave chip's own REG_MLX_SENSOR_VARIANT - see the
            expansion slave's own README.md section 4 for that
            register's own documentation. Not relayed on any other
            expansion_board_type, since there's no slave chip to relay
            to.
        Persists across power cycles the same way expansion_board_type
        does (F-RAM change-detection) - and is itself re-relayed to a
        freshly-reset expansion slave chip at this board's own next
        boot, since the slave chip has no persistent storage of its
        own to remember this across its own resets. Answered even
        during a declared critical error, same reasoning as
        0x110/0x190/0x1A0/0x1A2/0x1A4: this is configuration, not an
        actuation command. All 3 family members (MLX90640, MLX90641,
        MLX90642) are fully implemented on both the direct-connection
        path and the expansion slave's own relay path.

ID: 0x1A7 [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x1A6]
Query/response: MLX9064x sensor variant
DLC: any as a query (payload ignored) | 1 byte as a response
Data:
  - txData[0]: the currently-set mlx_sensor_variant value (see 0x1A6
               above)

ID: 0x1A8 [Master -> URTC Tool Head]
Request one chunk of the fault recorder (the "black box")
DLC: 1 byte or more (only the first byte is used)
Data:
  - rxData[0]: chunk index, 0 to 21. The record is 678 bytes, read in 22
               chunks of 32 bytes (the last chunk holds 6 real bytes; the
               rest of its 32 bytes are zero).
  Note: Answered whatever the active tool is, like 0x110. The firmware
        keeps the last 10 seconds before a fault in RAM and writes them to
        the F-RAM once, on the rising edge of the critical-error flag (see
        EEPROM.TXT section 7 for where). A chunk index out of range, or an
        F-RAM read that fails, gets no answer at all: silence cannot
        distinguish "no fault was ever recorded" from "the F-RAM is not
        answering". The export is raw, byte for byte: the firmware does not
        check the record before sending it, so the host checks the magic
        and the checksum itself.

ID: 0x1A9 [URTC Tool Head -> Master, answering 0x1A8]
One chunk of the fault recorder
DLC: 8 bytes, sent as four consecutive frames
Data:
  - the 32 bytes of the chunk in the order sent: frame 0 holds bytes 0-7,
    frame 1 bytes 8-15, frame 2 bytes 16-23, frame 3 bytes 24-31. If the
    transmit mailboxes run out in the middle, fewer than four frames
    arrive: treat that chunk as incomplete and ask again.
  Record layout (BlackBoxRecord_t, packed, little-endian, 678 bytes in all;
  version 2 of the record):
    offset 0     4 bytes   magic 0x424C4B42 ('BLKB' as bytes)
    offset 4     1 byte    struct_version (2)
    offset 5     1 byte    sample_count (how many of the 67 samples are real)
    offset 6     1 byte    write_index (where the ring was when it was flushed)
    offset 7     670 bytes 67 samples of 10 bytes, in ring order (the oldest
                           sample is at write_index when sample_count is 67)
    offset 677   1 byte    checksum: CRC-8/SMBUS (polynomial 0x07, initial
                           value 0) over bytes 0 to 676
  Sample (10 bytes): tick_ms uint32 (milliseconds since boot), active_tool
  uint8, current_temperature uint16 (degrees C), target_temperature uint16
  (degrees C), flags uint8 (bit 0 endstop triggered, bit 1 critical error
  flag - the first sample with it set is the fault itself, bits 2-3 thermal
  fault code). Samples are about 150 ms apart.

ID: 0x131 [Master -> URTC Tool Head]
Reset solder wire feeder position to 0
DLC: 4 bytes, magic payload 52 53 50 30 ("RSP0" in ASCII - Reset Spool
     Position 0)
Data:
  - rxData[0..3]: must be exactly 52 53 50 30 - any other payload (or any
               other DLC) leaves spool_position untouched, though this ID
               still answers with 0x132 regardless (reporting whatever
               the position actually is, unchanged) - same reasoning as
               0x192's own magic trigger: a corrupted or malformed frame
               landing on this ID by chance shouldn't be able to silently
               discard a real tracked position.
Effect: zeroes this tool's own open-loop spool_position tracker (see 0x132
        below) immediately in RAM, persisted to F-RAM the normal way (via
        SavedState_MaybeSave(), not forced immediately). Typically sent by
        the operator right after loading a fresh spool, since without a
        reset the tracked position keeps accumulating relative to
        whatever spool was loaded before, no longer meaning anything
        useful about the new one.

ID: 0x132 [Master -> URTC Tool Head, or URTC Tool Head -> Master answering
           0x131 or 0x132]

DLC: any as a query (payload ignored) | 4 bytes as a response
Data:
  - txData[0..3]: spool_position, signed 32-bit, big-endian (MSB to LSB).
               Positive = net fed forward since the last reset; negative
               = net retracted past it.
  Note: Open-loop estimate, not a physical measurement - this motor has
        no encoder, so this is this board's own running total of
        commanded 0x120 steps (assuming each one actually happened),
        the same open-loop assumption every other stepper on this board
        already makes. Persisted across power cycles in F-RAM
        (SavedState_t's own solder_spool_position field, see EEPROM.TXT) -
        restored directly on boot (not just held in recovered_state)
        since this is passive position tracking, not an actuator
        setpoint that could re-arm something hazardous by restoring it
        automatically.

ID: 0x135 [URTC Tool Head -> Master] (Automatic telemetry every 150ms)

        now - the Soldering Iron (its own original tool), or Hot Air

EXPANSION SLAVE BRIDGE (0x210-0x221) - see EXPANSION.TXT and

ID: 0x210 [Master -> URTC Tool Head]
Enter the expansion slave's own bootloader
DLC: 4 bytes
Data:
  - rxData[0..3]: Magic payload 0xB0, 0x07, 0x1D, 0x5A - same constant
                  this board's own application checks for its own CAN
                  0x7F0. Relayed to the slave's own application-mode
                  REG_ENTER_BOOTLOADER; this board doesn't check the
                  payload itself, the slave's own firmware does.

ID: 0x211 [Master -> URTC Tool Head]
Start slave firmware update
DLC: 8 bytes
Data: Same layout as this board's own CAN_ID_START_UPDATE (0x7F1) -
      big-endian total size (4 bytes) + big-endian HardwareID (4 bytes).
      Relayed to the slave's own bootloader-mode REG_START_UPDATE.

ID: 0x212 [Master -> URTC Tool Head]
Slave HMAC-SHA256 signature chunk, x4
DLC: 8 bytes
Data: Same 4-frames-of-8-bytes accumulation as this board's own
      CAN_ID_HMAC_CHUNK (0x7F7) - sent sequentially right after 0x211

DLC: 1-8 bytes

DLC: 8 bytes
Data: Same layout as this board's own CAN_ID_END_UPDATE (0x7F4) -

      below). Relayed to the slave's own bootloader-mode REG_END_UPDATE,
      which triggers its own size/CRC32/HMAC/anti-rollback verification

ID: 0x218 [URTC Tool Head -> Master, sent alongside 0x217's own response]
Slave bootloader version query, part 2 of 2
DLC: 2 bytes
Data:
  - txData[0]: Installed slave firmware's own version minor, low byte
  - txData[1]: The slave BOOTLOADER's own version (not the application's)

  - txData[2]: PATCH number of the installed slave application, 0xFF if
               not known

  - txData[4]: slave BOOTLOADER patch

        flashers read only the first 2 bytes of this frame.
  Note: Same 2-response-ID split as this board's own 0x7F9/0x7FA, for
        the same reason - the slave's 10-byte answer doesn't fit one
        CAN frame.

ID: 0x219 [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x219]
Slave bootloader verify-fail-reason query
DLC: any (request) / 1 byte (response)
Data:
  - txData[0]: The slave's own REG_VERIFY_FAIL_REASON byte
               (slaveboot_common.h's own VERIFY_FAIL_REASON_* constants -
               same values as this board's own CAN_ID_STATUS 0x7F5's
               2nd byte) - only meaningful right after 0x215 above
               reports STATUS_VERIFY_FAIL; stale (holds the previous
               update's reason) until the next verification failure.
               Same relay pattern as 0x215/0x216 - no response at all if
               the I2C transaction itself fails.

ID: 0x220 [Master -> URTC Tool Head]
Write slave application register (generic)
DLC: 2-8 bytes
Data:
  - rxData[0]: The slave's own application-mode register number
               (REG_PWM_*, REG_ADS_*, REG_MLX_* - see slave_common.h)
  - rxData[1..]: That register's own payload, relayed as-is
  Note: Only meaningful once the slave's own bootloader has already
        copied a verified application image into its main slot and
        jumped to it (see 0x210-0x218 above) - writing to an
        application-mode register while the slave is still in its own
        bootloader gets no response, same silent-failure convention as
        everywhere else in this bridge.
  Closed register list: the bridge relays only the registers below with
        the exact payload length shown (src/common/urtc_slave_regs.h);
        any other register, any other length, and in particular
        REG_ENTER_BOOTLOADER (0x02), are dropped without an answer.
          0x10 (0 bytes) 0x12 (1) 0x13 (1) 0x14 (1) 0x20 (2) 0x21 (0)
          0x30 (3) 0x31 (3) 0x32 (1)

ID: 0x221 [Master -> URTC Tool Head, or URTC Tool Head -> Master answering 0x221]
Read slave application register (generic)
DLC: 2 bytes (request) / up to 8 bytes (response)
Data (request):
  - rxData[0]: The register to read
  - rxData[1]: How many bytes to read back (caller's own responsibility
               to ask for the right length for whichever register it
               named - see slave_common.h for each register's own
               documented response length)
Data (response): Whatever the named register returned, exactly as many
                  bytes as requested.
  Closed register list: only 0x00 (max 1 byte), 0x01 (10), 0x11 (1),
        0x12 (32), 0x13 (32), 0x14 (1) and 0x22 (2) can be read; a length of
        0 or above the register's maximum, or any other register, gets no
        answer. One response frame still carries at most 8 bytes.
  Version register (0x01): the master reads all 10 bytes of it whatever
        length was asked, answers with the first bytes as above, and then
        sends 0x222.

ID: 0x222 [URTC Tool Head -> Master, only ever sent by the board]
Patch number of the slave application (companion of 0x221)
DLC: 2 or 3 bytes
Data:
  - txData[0]: The register the patch belongs to (0x01, the version
               register of the slave application)
  - txData[1]: The PATCH number of the slave application (1 to 127)
  - txData[2]: The low byte of the MINOR number of the slave
               application (byte 8 of its version register); optional
               for a reader, always sent by the master
  Note: The tenth byte of the version register used to be reserved and
        read 0. A slave application now puts its PATCH number there; the
        answer to 0x221 cannot carry it (one frame holds 8 bytes, the
        register has 10), so the master sends it here, right after that
        answer, and only when the byte is 1 to 127. A byte of 0 (a slave
        application from before the field) is ignored: no frame follows
        and a host takes the patch as unknown, exactly as before. The
        patch of the slave bootloader and of the application it holds
        are reported by the bootloader's own extension (0x218, 5 bytes).
        The answer to 0x221 holds the first 8 bytes of the register and
        stops at the HIGH byte of the minor number (byte 7), so no other
        frame carried the low byte (byte 8): the third byte of this frame
        does, and the whole minor is (byte 7 of the 0x221 answer) * 256 +
        txData[2]. A reader that takes only two bytes still gets the
        patch and shows the minor as unknown; a slave or a master from
        before the byte behaves as it always did.
        Nothing on the board listens for 0x222.

ID: 0x230 [Master -> URTC Tool Head]
Solder Paste Jetting Valve local PWM configuration
DLC: 3 bytes
Data:
  - rxData[0]: PWM channel (0-3, see docs/PINOUT_SLAVE.txt Block 4 for
               which physical connector pin each channel reaches)
  - rxData[1..2]: Frequency in Hz (uint16_t) [BIG-ENDIAN]
  Note: Thin, tool-specific wrapper over 0x220 above (writes the
        slave's own REG_PWM_CONFIGURE) - exists so a host controlling
        this specific tool doesn't need to also know the raw slave
        register map, same convenience every other tool's own dedicated
        ID already provides.

ID: 0x231 [Master -> URTC Tool Head]
Solder Paste Jetting Valve pulse
DLC: 3 bytes
Data:
  - rxData[0]: PWM channel (0-3)
  - rxData[1]: Duty percent, 0-100
  - rxData[2]: Pulse duration in milliseconds, 0-255 (0 = continuous,
               until explicitly stopped - not currently exposed by this
               tool's own command set, since a continuous jetting valve
               output isn't a documented use case for it)
  Note: Thin wrapper over 0x220 (writes the slave's own REG_PWM_PULSE).
        Genuine sub-millisecond pulse precision, since this PWM is
        generated locally on the expansion board's own TIM1, not routed
        from this board over a cable - see slave_pwm.c's own note on
        its 1us counter resolution.

=============================================================================
CAN BOOTLOADER PROTOCOL - see the README's "Building & Flashing" section
for the full walkthrough. These IDs are deliberately far from every
application-runtime ID above (0x095-0x255) so there's no risk of confusing
a bootloader-protocol frame with a normal command, or vice versa. 0x7F0 is
handled by the RUNNING APPLICATION; 0x7F1-0x7F4/0x7F7 are handled by the
BOOTLOADER (which only runs before the application, or after 0x7F0 resets
into it) - the application and bootloader never both listen for the same
ID, with 2 deliberate exceptions: 0x7F8 (query version) and 0x7FB (query
CAN error counters) are both answered by whichever one is currently
running, so a host can check what's installed - or diagnose the bus
itself - without needing to trigger a reset first.

Golden-image update model: every update is written into a backup/staging
flash slot first, never into the slot currently running. Only after it
fully passes size, CRC32, and HMAC-SHA256 signature verification does the
bootloader copy it into the main slot - which is never touched before that
point. See the README's flash memory layout section for the full reasoning.
=============================================================================

ID: 0x7F0 [Master -> URTC Tool Head, handled by the APPLICATION]
Enter bootloader mode
DLC: 4 bytes
Data:
  - rxData[0..3]: Magic payload, must be exactly 0xB0, 0x07, 0x1D, 0x5A
    Any other payload on this ID is ignored - this isn't just an ID match,
    specifically to make an accidental trigger from a corrupted or
    malformed frame extremely unlikely.
Effect: cuts power to every actuator inline (motors, heaters, laser -
        not deferred to a future loop iteration), then resets the chip.
        The bootloader takes over from here.

ID: 0x7F1 [Master -> URTC Tool Head, handled by the BOOTLOADER]
Start update
DLC: 8 bytes
Data:
  - rxData[0..3]: Total firmware image size in bytes (uint32_t) [BIG-ENDIAN]
  - rxData[4..7]: Declared HardwareID (uint32_t) [BIG-ENDIAN] - must match
    this board's own HardwareID exactly, or the update is rejected right
    here, before a single byte of flash is touched.
Effect: erases exactly as many 2KB pages of the BACKUP slot as the declared
        size needs (starting at 0x08024000 - the main slot is not touched).
        Replies with a 0x7F5 status frame (0x02 = erasing, then
        0x03 = receiving once erase completes).

ID: 0x7F7 [Master -> URTC Tool Head, handled by the BOOTLOADER]
HMAC-SHA256 signature chunk
DLC: 8 bytes
Data:
  - rxData[0..7]: 8 bytes of the expected 32-byte HMAC-SHA256 signature,
    sent as 4 sequential frames covering bytes 0-7, 8-15, 16-23, 24-31 in
    order. Send all 4 after 0x7F1 and before the first 0x7F2 data frame.
    Computed over the raw firmware image with a key shared between the
    bootloader and whatever tool signs the build - proves the image
    actually came from this project's own build process, not just that it
    arrived intact (which CRC32 alone only guarantees).

ID: 0x7F2 [Master -> URTC Tool Head, handled by the BOOTLOADER]
Firmware data
DLC: 1-8 bytes
Data:
  - rxData[0..DLC-1]: Raw firmware binary data, sent sequentially. CAN
    guarantees in-order delivery on a single bus, so no per-frame sequence
    number is included - the bootloader just appends whatever arrives to
    a 2KB page buffer in RAM, writes the page to the BACKUP slot once full
    (reading every half-word back and comparing it against what was meant
    to be written before considering the page done), and sends a 0x7F3
    acknowledgement before accepting the next page's data. A well-behaved
    master waits for each page's ACK before sending more, to avoid
    overrunning the bootloader's buffer.

ID: 0x7F3 [URTC Tool Head -> Master, sent by the BOOTLOADER]
Page written acknowledgement
DLC: 4 bytes
Data:
  - txData[0..3]: Index of the page that was just written (uint32_t)
    [BIG-ENDIAN], counting from 0 at the start of the backup slot.

ID: 0x7F4 [Master -> URTC Tool Head, handled by the BOOTLOADER]
End update / verify
DLC: 8 bytes
Data:
  - rxData[0..3]: CRC32 of the complete firmware image (uint32_t)
    [BIG-ENDIAN] - standard CRC-32 (reflected, polynomial 0xEDB88320,
    final XOR 0xFFFFFFFF), the same variant Python's zlib.crc32() computes.
  - rxData[4..5]: Firmware version major (uint16_t) [BIG-ENDIAN]
  - rxData[6..7]: Firmware version minor (uint16_t) [BIG-ENDIAN]. Optional
    PATCH extension (see "FIRMWARE PATCH NUMBER" below): the high byte,
    rxData[6], is always 0 in a legacy frame. A host MAY set it to
    0x80 | PATCH (PATCH 0-127) - but only towards a bootloader that
    announced support in the flags of 0x7E9. The minor itself stays in
    rxData[7].
Effect: the bootloader checks the backup slot's size, CRC32, and
        HMAC-SHA256 against what was declared. Only if everything matches
        does it copy the backup slot into the main slot (page by page, with
        the same read-back verification as above), then save the new
        metadata and reset into the updated application (0x7F5 status 0x04,
        verify OK). On any mismatch - size/incomplete transfer, CRC32,
        HMAC, or HardwareID - the main slot is never touched, 0x7F5 status
        0x05 (verify failed) is sent with a specific reason byte (see
        below), and the bootloader goes back to listening for a fresh
        attempt. It will never jump into an image that failed any of its
        checks.

ID: 0x7F5 [URTC Tool Head -> Master, sent by the BOOTLOADER]
Status
DLC: 1 byte normally, 2 bytes specifically for status 0x05 (verify failed)
Data:
  - txData[0]: 0x01 listening | 0x02 erasing | 0x03 receiving |
               0x06 verifying | 0x07 copying backup into main slot |
               0x04 verify OK (about to jump) | 0x05 verify failed |
               0xFF error (e.g. declared size of 0 or larger than the
               112KB slot)
  - txData[1] (only present when txData[0] == 0x05): reason code -
               0x01 incomplete transfer (didn't receive the declared size
               or all 4 HMAC chunks) | 0x02 CRC32 mismatch (transfer
               corruption) | 0x03 HMAC signature mismatch (not signed with
               this project's key) | 0x04 HardwareID mismatch (image built
               for different hardware - checked before a single byte is
               written, reported here for one consistent "why did it fail"
               path rather than the generic 0xFF error) | 0x05 rollback
               rejected (the image is validly signed, but declares a
               version older than what's already installed - only
               enforced when a currently-valid version exists to compare
               against, never on a blank board or one recovering from
               corrupted metadata. major and minor decide; the patch only
               takes part when BOTH the installed and the incoming version
               carry one, so an image declared without a patch is never
               rejected against the same major.minor)
  Note: the listening status 0x01 is sent when the listening window (about
        600 ms after power-up or reset) ends without a jump - because
        there is no valid application, or an update was requested - and
        again each time an aborted transfer returns to listening. It is
        NOT sent at the start of the window, which begins only after the
        bootloader has checked the stored application: a tool that wants
        to update sends its start-update frame (0x7F1) inside the window.

ID: 0x7F6 [URTC Tool Head -> Master, sent by the BOOTLOADER, every ~1s
while listening or mid-update]
Heartbeat
DLC: 2 bytes
Data:
  - txData[0]: same status codes as 0x7F5 (always just the bare status
    byte here, never the 2-byte verify-fail-with-reason form - the
    heartbeat's own second byte is always the progress percent below, not
    a reason code)
  - txData[1]: progress percent, 0-100, or 0xFF where not applicable (e.g.
    while listening)
Note: the heartbeat stays at DLC 2 on purpose. Released flashers read it only
        when the length is exactly 2, so a longer heartbeat would blind them
        (no progress, no page-ack retry check). The PATCH number does not
        travel here; see 0x7E9.
Effect: none - purely informational. Lets the master distinguish "node is
        alive but hasn't started listening yet" from "node is completely
        unresponsive," and gives visibility into a stuck bootloader without
        waiting for a timeout.

ID: 0x7F8 [Master -> URTC Tool Head, handled by BOTH the application AND
the bootloader, whichever is currently running]
Query version
DLC: any (payload ignored)
Data: none needed
Effect: whichever side is currently running answers with 0x7F9. Unlike
        every other ID in this section, this one isn't bootloader-specific -
        it works whether the board is running its normal application or
        sitting in the bootloader, so a host can check what's currently
        installed without first triggering a reset via 0x7F0 just to find
        out. Safe to send at any time; read-only, no side effects either side.

ID: 0x7F9 [URTC Tool Head -> Master, sent by whichever side answered 0x7F8]
Version response
DLC: 8 bytes
Data:
  - txData[0]: 0x00 = answering as the running application, 0x01 =
    answering as the bootloader
  - txData[1..4]: HardwareID (uint32_t) [BIG-ENDIAN]
  - txData[5..6]: Firmware version major (uint16_t) [BIG-ENDIAN]
  - txData[7]: Firmware version minor (uint8_t)
Notes: when the bootloader answers (txData[0]=0x01), the HardwareID/version
       reported are whatever the metadata page currently says about the
       main slot - i.e. what's actually installed and would run if jumped
       to, not necessarily "what the bootloader itself is". If the
       bootloader has no valid metadata (blank chip, or every check
       failed), it reports HardwareID=0 as a sentinel - a real
       THIS_HARDWARE_ID is never zero, so a host can tell "bootloader
       running with nothing valid installed" apart from "bootloader
       running, main slot looks fine, just hasn't jumped yet for some
       other reason" (e.g. an update was requested). See 0x7FA below for
       the bootloader's OWN version, sent alongside this frame whenever
       the bootloader itself is the one answering.

ID: 0x7FA [URTC Tool Head -> Master, sent ONLY by the BOOTLOADER,
alongside 0x7F9, whenever the bootloader is the one answering 0x7F8]
Bootloader version response
DLC: 3 bytes
Data:
  - txData[0]: Bootloader version major (uint8_t)
  - txData[1]: Bootloader version minor (uint8_t)
  - txData[2]: Bootloader version patch (uint8_t)
Notes: this is bootloader_common.h's own version (BOOTLOADER_VERSION_MAJOR/MINOR/
       PATCH in the source) - a separate thing from 0x7F9's Firmware
       version major/minor, which describes the installed APPLICATION,
       not the bootloader itself. The application never sends this frame -
       it has no way to know a currently-flashed bootloader's version
       other than this, so if the application is the one answering 0x7F8,
       only 0x7F9 arrives and this one doesn't. A host that wants both
       needs the board sitting in the bootloader when it asks (e.g. right
       after 0x7F0, or on a fresh boot before the application has been
       jumped to).

ID: 0x7E9 [URTC Tool Head -> Master, sent by whichever side answered 0x7F8,
right after 0x7F9]
Version patch response (optional companion of 0x7F9)
DLC: 3 bytes
Data:
  - txData[0]: answering side, same values as 0x7F9 byte 0 (0x00 =
               application, 0x01 = bootloader)
  - txData[1]: PATCH number of the installed application (what the
               application reports about itself, or what the bootloader
               recorded for the image installed in the main slot), or 0xFF
               when it is not known (blank board, image installed by a
               bootloader or a flasher that predates the patch extension)
  - txData[2]: flags. bit 0 = this bootloader reads the PATCH number from the
               high byte of the minor field of 0x7F4 / 0x214 (always 0 when
               the application answers). Other bits are 0 and reserved.
Notes: 0x7F9 and 0x7FA are unchanged - 0x7F9 already uses all 8 bytes of a
       classic CAN frame and released flashers read 0x7FA only at length 3 -
       so this ID carries the patch instead. It is TX-only (nothing listens
       for it on the board). A board that predates the extension never
       sends it: a host that gets 0x7F9 and no 0x7E9 within a short grace
       window (300 ms) must treat the patch as unknown and must keep using
       the legacy two-component version and the legacy 0x7F4 / 0x214 payload.
       The application's own major.minor.patch is therefore
       (0x7F9 major, 0x7F9 minor, 0x7E9 txData[1]).

ID: 0x7FB [Master -> URTC Tool Head, handled by BOTH the application AND
the bootloader, whichever is currently running]
Query CAN error counters
DLC: any
Effect: whichever side is currently running answers with 0x7FC. Same
        dual-answerable convention as 0x7F8/0x7F9 above - useful for
        telling a genuine bus problem (wiring, termination, bitrate
        mismatch) apart from an application/bootloader-side issue during
        a slow or stuck update, without needing to know in advance which
        side is currently running.

ID: 0x7FC [URTC Tool Head -> Master, sent by whichever side answered 0x7FB]
CAN error counter response
DLC: 2 bytes
Data:
  - txData[0]: TEC (Transmit Error Counter), 0-255
  - txData[1]: REC (Receive Error Counter), 0-255
  Note: Read directly from the CAN peripheral's own ESR register (REC in
        bits 31:24, TEC in bits 23:16) rather than tracked in software -
        the peripheral already maintains these per the CAN bus protocol's
        own fault-confinement rules (error-active below 128, error-passive
        128-255, bus-off at TEC>255 specifically). A steadily climbing TEC
        with no corresponding REC growth typically points at this board's
        own transmissions going unacknowledged (no other node on the bus,
        or a wiring/termination problem specific to this board's own
        connection), not a fault in this board's own command handling.

ID: 0x7FD [Master -> URTC Tool Head, handled by THIS bootloader only]
Authorize downgrade for the current update attempt
DLC: 4 bytes
Data:
  - rxData[0..3]: Magic payload 0xD0, 0x9E, 0x12, 0xAD
Effect: bypasses HandleEndUpdate's own anti-rollback check (see 0x7F4
        above) for THIS update attempt only - installing a validly-signed
        image with a version older than what's already running is
        normally rejected (verify-fail reason 0x05) specifically so a
        version with a since-discovered vulnerability can't be replayed;
        this command exists for the genuine, occasionally-needed case of
        deliberately reverting to an older release. One-shot: reset to
        unauthorized at the start of every fresh 0x7F1 (so it must be
        sent again for each attempt that needs it, never carries over to
        an unrelated later update), and consumed the moment 0x7F4's own
        anti-rollback check runs, whether or not the version actually
        turned out to need it. Sending this does NOT skip re-uploading
        the firmware itself - the full image still goes through
        0x7F1/0x7F2/0x7F7/0x7F4 exactly as any other update would, only
        the version-ordering check is bypassed.
  Session: honoured only in a bootloader session that the application
        started by accepting 0x7F0 (it leaves a mark that the bootloader
        reads once at start-up and clears), or when no valid application
        is installed, so that a board can still be recovered. A 0x7FD
        that arrives after a power-up, or after a reset of any other
        cause, is ignored. Send 0x7F0 first, as the Flasher does. The
        restriction is a bootloader build option
        (URTC_BOOT_RESTRICT_UNSAFE_COMMANDS, on by default).

ID: 0x7FE [Master -> URTC Tool Head to start; URTC Tool Head -> Master for
every reply, handled by THIS bootloader only]
Read back the main slot's own current contents
DLC: any (request) / 4 bytes (first reply only) / 8 bytes (every reply
after that)
Data (first reply): big-endian total byte count currently installed
        (from the stored metadata's own size field), or 0 if there's
        nothing valid installed to back up. Distinguished from every
        later reply purely by DLC (4 vs 8) - no separate "here's the
        size" side-channel needed.
Data (every reply after the first): raw bytes from the main slot,
        sequential starting at its own base address, 8 bytes per frame.
Effect: the CAN equivalent of the Flasher's own "back up entire flash
        before erasing" SWD feature - reads the CURRENTLY INSTALLED
        firmware back over the bus, unmodified, before deliberately
        overwriting it (a normal update, or one authorized via 0x7FD
        above). Read-only, never touches flash - safe to request any time
        the bootloader is idle; ignored while an update is already in
        progress. Paced by CAN_ID_READBACK_PAGE_ACK below: the bootloader
        sends one 2048-byte page (256 frames), then waits up to 3s for
        that exact page to be acked before sending the next one - the
        transfer is abandoned (silently stops sending) if a page goes
        unacked, the same way a stalled write-direction transfer would
        eventually time out on the Flasher's own side instead.
  Session: like 0x7FD, answered only in a bootloader session that the
        application started by accepting 0x7F0, or when no valid
        application is installed; ignored in any other session.

ID: 0x7FF [Master -> URTC Tool Head, handled by THIS bootloader only]
Read-back page acknowledgement
DLC: 4 bytes
Data:
  - rxData[0..3]: Big-endian page index being acknowledged (0-based) -
        same big-endian-page-index convention as CAN_ID_PAGE_ACK, just
        the opposite direction: here the HOST is confirming it safely
        received and stored a page the bootloader sent, not the
        bootloader confirming a page the host sent.

FIRMWARE PATCH NUMBER (major.minor.patch over CAN) - backwards compatible
-----------------------------------------------------------------------------
Until firmware 0.3.5 only major and minor travelled. The patch now travels in
three additive places; nothing a released flasher reads changes:

  1. 0x7E9 (new, DLC 3): installed application patch + capability flags, sent
     by the application and by the main bootloader right after 0x7F9.
  2. The high byte of the 16-bit minor field of 0x7F4 / 0x214 (always 0 in a
     legacy frame): 0x80 | PATCH.
  3. Slave version answer 0x218: DLC 5 instead of 2 (see above).

Frames that could NOT be extended, and why: 0x7F9 and 0x7F4 are already 8
bytes (the classic CAN maximum); 0x7F6 (heartbeat) and 0x7FA are read by
released flashers only at exactly DLC 2 and DLC 3, so lengthening them would
make those flashers ignore them.

Stored form. The bootloaders keep the minor field exactly as received in
their metadata page, so the page layout is unchanged. Anywhere a minor is
reported to the host as a number (0x7F9 byte 7, the slave 0x217/0x218 minor)
only the low byte is used.

Anti-rollback. Compared as major, then minor, then patch - the patch only
when both versions carry one. A legacy flasher (no patch) can keep
re-installing the same major.minor over a board that knows its patch.

HOST CONTRACT (for URTC-FLASHER / URTC-WEB-STUDIO; reference behaviour, in
Python; URTC-FLASHER and URTC-WEB-STUDIO are not changed by this document)

    PATCH_UNKNOWN = 0xFF
    PATCH_FLAG = 0x80

        can.send(0x7F8, b"\x00")
        # ... collect 0x7F9 (len 8) and, for a bootloader, 0x7FA (len 3) as
        # today. Additionally collect 0x7E9 (len >= 3, ignore extra bytes):
        #     side, app_patch, flags = data[0], data[1], data[2]
        # After 0x7F9 arrives wait at most patch_grace for 0x7E9 (the
        # bootloader case already waits for 0x7FA; wait for both together).
        return {
            ...,                                   # existing keys unchanged
            "version_patch": None if app_patch == PATCH_UNKNOWN else app_patch,
            "patch_aware": seen_7e9,               # False = board predates it
            "accepts_patch_in_end_update": bool(flags & 1),
        }

    def end_update_payload(crc32, major, minor, patch, board):
        # Send the patch only to a bootloader that announced bit 0 of the
        # flags in ITS OWN answer (query again once the bootloader is
        # listening, not the application's answer).
        if board["accepts_patch_in_end_update"] and patch is not None:
            minor_field = ((PATCH_FLAG | (patch & 0x7F)) << 8) | (minor & 0xFF)
        else:
            minor_field = minor
        return struct.pack(">IHH", crc32, major, minor_field)

    def compare(installed, candidate):             # (major, minor, patch|None)
        # decide on major and minor; use the patch only when both have one
        ...

    def slave_version(can):
        # 0x217 as today (>= 8 bytes); 0x218: len >= 2 as today, and when
        # len >= 5: app_patch = d[2] (0xFF = unknown), boot_minor = d[3],
        # boot_patch = d[4], and the slave bootloader accepts the patch in
        # the minor field of 0x214.

A new flasher with an old board: no 0x7E9 -> patch unknown, legacy 0x7F4 -
works as before. An old flasher with a new board: ignores 0x7E9, reads 0x7F9,
0x7FA, 0x7F6 and 0x217/0x218 exactly as before, and its legacy 0x7F4 is
accepted.

APPENDIX. SEVERAL TOOL HEADS ON ONE BUS (MULTINODE, OFF BY DEFAULT)
-----------------------------------------------------------------------------
Implemented in the firmware behind a switch (0x1AC / 0x1AD above) that is OFF
by default. Tested on the host only; it has not been tried on boards. The
design, the failure modes and the safety rules are in URTC-COMMON/docs/
MULTINODE.md; the identifiers are in its spec/can_protocol.json (section
"multinode"). With the switch off none of the frames below exists for the
firmware: every identifier of this file keeps its meaning and its behaviour.

With the switch ON, the node address is the value of the five ID jumpers
(0-31), and the identifiers 0x400-0x49F are used (all multi-byte fields
big-endian, a lower identifier wins arbitration):

  Frame 0x400          DISCOVER, host to all: mn_version (1), slot_ms (1-50).
                       Each node answers NODE_INFO after address x slot_ms.
  Frame 0x401          SELECT, host to all: action (0 deselect all, 1 select),
                       node (0-31), seq. Only the selected node obeys the
                       identifiers of this file. A selection lapses after
                       2 s unless it is repeated.
  Frame 0x402          SAFE_STOP, host to all: reason. Every node, selected
                       or not, puts its tool in the safe state (heaters off,
                       motion stopped, outputs released). It does not latch.
  Frame 0x420 + node   NODE_INFO: tool, state, instance, mn_version, serial
                       (u32, from the unique device ID).
  Frame 0x440 + node   NODE_STATUS every second: state (0x01 selected, 0x02
                       fault, 0x04 conflict, 0x08 bootloader), error code,
                       uptime in seconds (u16).
  Frame 0x460 + node   NODE_CMD, host to one node: func (u16), up to 6 bytes.
                       The firmware answers only func 0x110 (status), with
                       NODE_RESP 0x480 + node carrying the six bytes of 0x111.
                       Anything else is ignored: this form never actuates.

Behaviour of a node with the switch on:
  - First 1.5 s after start it listens. A node that hears another node starts
    unselected; one that hears nobody behaves as the one head on the bus
    (legacy mode), so a host that knows nothing of the extension keeps working
    with a single head. During the listening window single-head frames are
    not obeyed.
  - A node that is not selected ignores every identifier of this file,
    including 0x7F0 (enter bootloader) and 0x7F8 (version query), sends no
    single-head telemetry and never actuates. A firmware update therefore
    begins with SELECT.
  - Two boards on one address: each hears the other's NODE_INFO or
    NODE_STATUS on its own address, latches CONFLICT, puts its tool in the
    safe state and ignores commands until the next power-up. The status keeps
    reporting CONFLICT.
  - The microcontroller keeps authority: thermal protection, limits and
    watchdogs run as always. A lapsed or withdrawn selection does not by
    itself switch an output off (a held electromagnet stays as it is); each
    tool's own communication watchdog acts as in single-head mode.
  - The bootloader does not take part: its frames (0x7F0-0x7FF) reach only the
    selected application node; once a node is in its bootloader it is the only
    one that should be on the bus being updated.
  - The collision frame 0x095 of the scan probe is sent whatever the
    selection, as an event.

### 0x222 SLAVE_APP_PATCH - Patch number of the slave application (companion of 0x221)

board to host; handled by the application; tools: any.

response, DLC 2-3

| Byte | Width | Type | Field | Values | Note |
|---|---|---|---|---|---|
| 0 | 1 | u8 | register |  | The register the patch belongs to: 0x01, the version register of the slave application. |
| 1 | 1 | u8 | patch | 1..127 |  |
| 2 | 1 | u8 | minor_low | optional | The low byte of the minor number of the slave application (its byte 8 of the version register, which the 8-byte answer to 0x221 cuts off); with the high byte, byte 7 of that answer, it is the whole minor.
