=============================================================================
URTC - VERSION BUMP CHECKLIST
=============================================================================
Built after the 1.0 -> 1.1 migration, which took 4 separate correction
rounds with the user to find everything - each round using a grep
pattern that missed a different real case. Rewritten completely after a
later reorganization retired the dual monolithic/partitioned form and
the VX.X/ version-numbered subfolder scheme project-wide - the original
version of this document described a folder/file layout that no longer
exists at all. This document exists so the NEXT bump doesn't repeat
either round's mistakes. Read this top-to-bottom before touching
anything; don't just grep for the old number and replace it blindly -
several of these entries explain why a match should NOT change.

AMENDMENT: Track A's application-firmware version is no longer "bumped
only on explicit request" (see that section below) - it's now
mechanized and incremental, same odometer-carry mechanism as Tracks C/E
(bump_version.py at the repo root, called by build_firmware.sh/.bat
before compiling each of the 4 components). Flasher and Tester also no
longer live in this repo under tools/ - they're the separate
URTC-FLASHER and URTC-TESTER repos now, each with its own independent
version. Several path references below (tools/flasher/, tools/tester/)
predate that split and are historical, not current guidance - see each
repo's own README for its current layout.

There are FIVE independent version tracks in this project now (a new
Track E was added once the expansion slave chip's own firmware existed -
the original 4-track version of this document predates that chip). Confusing
which track a given "1.0" belongs to is exactly what caused every miss
in the last migration.

TRACK A - MAIN BOARD APPLICATION FIRMWARE VERSION (MAJOR.MINOR.PATCH,
currently 0.2.x)
-----------------------------------------------------------------------------
Covers ONLY the main board's own application firmware now - Flasher and
Tester moved to their own repos (URTC-FLASHER, URTC-TESTER) with their
own independent version numbers, no longer sharing this one. This track
is fully MECHANIZED like Tracks C/E: bump_version.py (repo root), called
by build_firmware.sh/.bat as the first step of compiling this
application, bumps PATCH by 1 on every real build, with the same
odometer-carry rule (see Track C's own note for the full mechanism).
That same bump also mirrors the new version into
src/F303-master/boot/bootloader_common.h's own FIRMWARE_VERSION_* copy
(see that header's own comment for why it keeps a separate copy) - never
hand-edit that copy, it will just drift again.

  There is nothing to do here anymore. The VX.X/ version-numbered

--- A3. Compiled binary naming ---
  firmware/URTC_MAIN_FIRMWARE_v<MAJOR>.<MINOR>.<PATCH>.bin/.hex/.elf
  --> UNIFIED convention as of the naming-convention-unification bump
      (see CHANGELOG.md): all 4 components now share ONE pattern,
      <PREFIX>_v<MAJOR>.<MINOR>.<PATCH> - same convention sibling repo
      HYDRA-UMC's own build_firmware.sh already used from the start. This
      REPLACED the old A3/C/E2 policy (main application versioned,
      MAJOR.MINOR only, no PATCH; the 2 bootloaders and the slave
      application unversioned) - that old policy is derogated, not just
      for this one bump. The 4 prefixes: URTC_MAIN_BOOTLOADER,
      URTC_MAIN_FIRMWARE, URTC_SLAVE_BOOTLOADER, URTC_SLAVE_FIRMWARE.
      Delete the old-numbered/old-named binaries after confirming the new
      ones build and byte-compare correctly against a fresh compile (move
      them to SONNET/_papelera/, never a permanent delete, per this
      project's own no-permanent-delete convention).
  --> Only ONE set of these 3 files exists now, not a monolithic-plus-
      partitioned pair (the "_partitioned" suffix was dropped project-
      wide when the monolithic form was retired) - don't recreate that
      suffix on a future bump.
  --> Bootloader binaries DO include a version number in the filename
      now (URTC_MAIN_BOOTLOADER_v..., URTC_SLAVE_BOOTLOADER_v...) - see
      Track C, this reverses that track's own former "never" policy.
  --> The expansion slave chip's own application binary is now named
      URTC_SLAVE_FIRMWARE_v<MAJOR>.<MINOR>.<PATCH>.* (previously
      URTC_SLAVE_APP.*, unversioned) - still doesn't move WITH Track A's
      own numbers (each component's version is independent), but its
      filename does now carry ITS OWN version - see Track E.
  --> generate_manifest.py locates each component's real .bin via a glob
      for <PREFIX>_v*.bin in firmware/ (not a hardcoded name), so it can
      never silently drift out of sync with what build_firmware.sh/.bat
      actually produced.

--- A4. OLED boot splash (firmware, NOT a text string) ---
  firmware_render.c: SplashYellowText[2][128]
  --> The "URTC vX.X" text on the OLED at boot is a pre-rendered SSD1306
      bitmap baked into this const array, not something OLED_PrintStr()
      draws at runtime - editing it means decoding/re-encoding pixel
      columns, not a text replace. Technique that worked: render the
      current array to an actual PNG (a short Python/PIL script, 8x
      scale) to visually confirm the current digit, find the exact empty
      "separator" columns bounding just that one digit (a column is
      fully 0x00 in both page bytes = boundary), replace only those
      columns with an existing glyph shape already present elsewhere in
      the same bitmap (e.g. reuse the "1" from "v1" to build the new
      minor-version digit) centered in the same column span so nothing
      else in the strip shifts, then render the candidate again before
      touching the actual source. Verify with a byte-diff against a
      fresh compile afterward - a correct edit here changes zero bytes
      of binary size (only values inside an already-existing array).
  --> The GIF preview of this splash (ani/splash_boot.gif) is decoded
      straight from this same array by a one-off script, not maintained
      by hand - regenerate it the same way after any edit here rather
      than trying to hand-edit the GIF, so it can never drift from what
      the real firmware actually shows.

  and doesn't try to hand-edit it before a release.

    hand-edit this to correct a mistake - a normal build already bumps
    it automatically, see above)

      firmware's table just above it - don't add bootloader entries to
      the firmware table or vice versa)

      URTC_MAIN_BOOTLOADER_v<MAJOR>.<MINOR>.<PATCH>.bin/.hex/.elf. This
      REVERSES the old "never" policy - see A3's own note for when and

  --> This bootloader's own folder (src/F303-master/boot/) is a flat,

TRACK D - NEVER CHANGES ON ANY VERSION BUMP (false positives to
recognize and leave alone, not "fix")
-----------------------------------------------------------------------------
  - Changelog entries and auditoria_historial.txt entries - historical
    record by definition, describes what a past version WAS, not what
    the current one is
  - chat.TXT's deliberate warning text about old path naming (see A6) -
    including the section documenting the VX.X/ folder scheme's own
    retirement; that's the historical record of a real past event, not
    live guidance to follow again
  - License version numbers that aren't this project's own: "CC BY-SA
    4.0", "GPL-3.0", "CERN-OHL-S v2", "Apache License, Version 2.0" (the
    3 vendored Melexis sensor libraries' own license header)
  - Binary file metadata embedded by unrelated third-party tools (found
    once: a JPEG's own "CREATOR: gd-jpeg v1.0" EXIF-adjacent string -
    the version of the JPEG library that processed the image file,
    zero relation to this project)
  - Tkinter text-widget position indices - "1.0" is literally Tkinter's
    own syntax for "line 1, character 0" (start of a text widget's
    content), appears in both PC tools' code wherever they read/insert
    text-box contents - not a version number, don't touch
  - Bare numeric literals that happen to read "1.0" in code - timeout
    values in seconds (`timeout=1.0`), scroll-position fractions
    (`yview_moveto(1.0)` = 100%), interpolation fraction tuples - check
    the actual surrounding code before assuming any bare "1.0" is a
    version
  - Mentions of an external tool's OWN version number in an explanatory
    comment (found once: a comment noting that pyOCD, a third-party
    library, "hasn't reached its own 1.0 release yet" - unrelated to
    URTC's version)
  - The root README's own top-of-document "constant evolution" note
    (added per the user's own explicit request) - this
    is deliberate, permanent framing text explaining that the project
    has no tagged Release yet, not something to remove once a version
    number exists somewhere else in the document

LESSONS FROM THE 1.0 -> 1.1 MIGRATION, AND THE LATER MONOLITHIC-FORM
RETIREMENT (why this document exists, and why it needed a full rewrite)
-----------------------------------------------------------------------------
Every one of these caused a real, separate correction round with the
user. Read them once so the pattern is familiar, not just the specific
instance:

1. Anchoring a grep pattern to "v1.0" or "V1.0" (the letter immediately
   before the number) misses a bare "1.0" with no v/V directly attached,
   e.g. "**Version:** 1.0". Search for the number itself as a fallback
   pass: `\b1\.0\b`, then manually triage every hit using Track D above
   to rule out false positives - there will be many, that's expected and
   fine, the point is not missing a true positive because a narrower
   pattern already felt exhaustive.
2. Duplicate copies of the same asset in more than one folder (images/
   at the project root vs. tools/*/assets/) are easy to update in
   one place and forget in the other, since a single `find`/`grep` scoped
   to "the tool's own folder" won't surface the root-level duplicate at
   all. Explicitly check for a project-root images/ (or similar shared-
   assets) folder every time, independent of the per-tool folders.
   `find /project-root -iname "*.png" -o -iname "*.svg"` from the very
   top, not from inside each tool's folder, is what actually catches this.
3. A "screenshot" of an app window is a real capture of a specific past
   run, not a template - it goes stale the moment the version-visible
   parts of the UI it captured change, and grep can't find this at all
   because there's no text to search, just pixels. Anything in the repo
   that's an actual app screenshot (as opposed to a designed logo/banner)
   needs to be explicitly regenerated by re-running the real app, every
   version bump that touches anything visible in that screenshot.
4. Distinguishing "this document's title just borrows the project's
   name+version as a label" from "this document's content is tied to a
   physical hardware revision that hasn't changed" takes actually
   reading what the document is ABOUT, not just noticing the same
   version string pattern in both. When genuinely unsure which side a
   given file falls on, the content of the document is the tell: does it
   describe physical pin/component/dimension facts that only change if
   the PCB itself changes (Track B), or protocol/behavior facts that live
   in firmware/software (Track A)? A BOM or pinout is never Track A. A
   CAN command map or an EEPROM byte layout is never Track B.
5. When something doesn't compile to code (a README title, an SVG text
   element, a baked-in OLED bitmap), the fix isn't optional or lower-
   priority just because it's not source code - the OLED splash bitmap
   in particular is easy to forget entirely since it never shows up in
   any text-based grep at all (it's a byte array, not a string).
6. A checklist document like this one is itself subject to going stale -
   this exact document described a VX.X/ folder scheme and a monolithic-
   plus-partitioned file pair for months, right up until both were
   retired in one pass, and nobody updated this file to match until a
   later, separate request pointed out that "version change files"
   needed updating too. A structural project change big enough to touch
   file paths, binary names, or how many forms of a file exist is big
   enough to also require re-reading (and likely rewriting parts of)
   this checklist itself - it's not a write-once reference.
7. A brand-new document created after this checklist's own last update
   (docs/TOOLS.TXT, added alongside the 13-tool expansion) won't appear
   anywhere in an old copy of this checklist at all, and a version-bump
   pass that only follows the existing entries here will silently skip
   it. When performing an actual version bump, cross-check the current
   real file tree against this document's own entries first, rather
   than trusting this list to already be complete - new files get added
   between checklist revisions more often than this document itself
   gets revised to mention them.
