> **⚠️ 安全上の注意：** 本ボードは**10W のレーザー彫刻ダイオード**と複数の加熱ステージ（T12 はんだごてカートリッジ、3D プリンターのホットエンド）を駆動します。これを組み立てて使用するということは、適切な安全対策（ダイオードの波長に対応したレーザーゴーグル、熱保護、手の届く電源遮断装置）なしに組み立てたり操作したりすると**火傷、火災、または眼の損傷**を引き起こしうる機器を扱うことを意味します。これは現状のまま共有されているホビイスト/メーカー向けのプロジェクトです——構築および使用は自己責任で行い、ファームウェアにウォッチドッグがあるからといって基本的な安全対策を省略しないでください。

こんにちは！私がずっと開発してきた URTC（Universal Robot Tool Controller）というプロジェクトを紹介したいと思います。これは、ロボットアームや自動化セットアップの能力を拡張するために特別に設計された、単一構造の高集積制御ボードです。[Source-Robotics](https://source-robotics.com/)（[GitHub](https://github.com/Source-Robotics)）が設計・開発した 2 つのオープンソースロボットアーム、PAROL6 と Faze4 のようなプラットフォームに最適です。

**URTC は独立した非公式プロジェクトです。** Source-Robotics によって開発または承認されたものではありません——PAROL6 と Faze4 とうまく連携するように構築された互換性のあるツールヘッドコントローラーであり、同じ CAN ベースのアーキテクチャは他のロボットアームプラットフォーム向けに適合させることにも開かれています。

以下は、それが何であるか、何をするか、そして現在管理しているハードウェアエコシステムの完全な内訳です。

**状態：🚧 積極的に進化中のプロジェクト——まだリリースはありません。** URTC は、ファームウェア（新しいツールプロファイル、拡張スレーブのエコシステム、プロトコルの変更）とハードウェア（回路図と BOM はまだ最終決定されておらず、実装されたボードはまだ存在しません）の両面で同時に、継続的かつ積極的に開発が進められています。両側が一緒に動き続けているため、任意の時点で本リポジトリにあるものは、安定したバージョン管理された製品ではなく、進行中の作業のスナップショットです——ファイル名、フォルダ構造、ツール数、そしてドキュメントは、設計が落ち着くまですべて変わる可能性があります。ファームウェアとハードウェアの両方が本当に安定した、実機で検証された状態に達したら、すべて（ファームウェア、ブートローダー、PC ツール、ハードウェア設計ファイル、ドキュメント）を、一貫した凍結されたスナップショットとしてまとめた正式な **リリース** がタグ付けされます。それまでは、`main` を実際にそうであるところの、積極的に動き続ける対象として扱ってください。

## ⚙️ URTC とは？

URTC は、STM32 マイクロコントローラー（STM32F303CCT6、LQFP48）を搭載した、オールインワンのコンパクトな制御ボードです。CAN バス経由でメインのロボットコントローラーと通信し、ツールヘッドや軸のすぐそばで、複雑なタスクをリアルタイム・低レイテンシーで実行できます。即座の診断のための板載 OLED ディスプレイ——アニメーション起動スプラッシュ、ツールごとのアニメーションアイコン、2 トーンパネル上のリアルテレメトリ——単一ピクセルの RGB ステータス LED、カメラ照明用のアドレス指定可能な RGB LED リング、アドオンボード用の 20 ピン拡張コネクタ、電源喪失時にもアクティブツールの設定値を保持する板載 F-RAM、そして専用のアナログおよび大電流電源ステージを備えています。

## 🛠️ スケーラブルなアーキテクチャとツールマトリクス

URTC の核となる強みは、その極めて高い汎用性です。すべての異なる作業ごとに電子機器を交換するのではなく、本ボードはスケーラブルなマトリクスアーキテクチャを備えています：

* **32 アドレス識別方式：** ハードウェアと通信プロトコルは、5 ビットのはんだジャンパー ID マトリクス（ID0-ID4）を介して、ロボットヘッド上で直接最大 32 種類の異なるツールまたはエンドエフェクタを識別できるように設計されています。この 32 通りの読み取りのうち、31 通りは直接ツールプロファイルにマッピングされます。32 番目（5 つのジャンパーすべてが取り付けられた状態、`11111`）は代わりに「フリー構成」アドレスとして予約されています——下記参照。
* **25 種類のプラグアンドプレイ自動プロファイル：** ファームウェアは 25 種類のツールプロファイルをネイティブに処理します——ボードはツールヘッドの物理的な識別情報を読み取り、完全な再書き込みを必要とせずにシームレスに電源ステージ、センサー、ロジック切り替えを構成します。既存の方式の中に、将来のツールプロファイル用に 6 つのアドレスが空いたまま残っています。
* **フリーツール構成：** 予約された `11111` のジャンパー読み取りは固定のツールを選択するのではなく、代わりに、CAN 経由（`URTC Flasher` 経由）で事前に設定された、自身の永続的な F-RAM 内のレジスタからどのツールを使用するかを調べるようボードに指示します。物理的にジャンパーをはんだ付けし直すことなく、異なるツールへ再プログラムする必要があるボードに便利です。完全な仕組みは `docs/EEPROM.TXT` 第 5 節を参照してください。

## 🔌 ハードウェアの柔軟性とモーターサポート

これほど幅広いアプリケーションに対応するため、URTC のハードウェアは以下を制御する能力を完全に備えています：

* **NEMA ステッピングモーター：** NEMA 8、11、14、17 は板載の TMC2209 から直接駆動され、NEMA 23 と 34 も同様です——メインボード自身のドライバーステージ経由で、いずれも最大 **2.0A** まで対応します。NEMA 23/34 が定格の全トルクを発揮するには、拡張コネクタ上の TMC5160（下記参照）が最大 **10A** をサポートし、その電流は該当ボード向けに選ばれた外部 MOSFET/センス抵抗によってスケーリングされます——モーターが拡張ドライバーへ移動した時点で、板載の 2.0A 制限は適用されなくなります。
* 高精度な動作のための**3 相ブラシレス／ジンバルモーター**。
* 閉ループ制御のための**ホールセンサーとタコメーター付きモーター**。
* TCRT5000 のような反射型光学近接センサー向けの**専用入力**に加え、4 つのツールプロファイル間で共有される汎用のアクティブロー方式のエンドストップ/リミットスイッチ入力。

## 🧩 拡張コネクタ

特定のツールプロファイル単体が公開するもの以上を必要とするアドオンボード（追加のステッピング軸（TMC2209 または TMC5160）、2 つ目のセンサーボードなど）向けの、ツール専用コネクタとは別の 20 ピンヘッダーです。

| ピン数 | 信号 |
|---|---|
| 4 | 24V |
| 1 | 3.3V |
| 1 | 5V |
| 3 | GND |
| 2 | ビットバンギング I2C（SCL/SDA）——OLED/F-RAM のハードウェア I2C2 とは別の独自バス |
| 3 | STEP/DIR/EN——以下のどちらのドライバーチップにも共通 |
| 4 | ビットバンギング SPI（CS/SCK/MISO/MOSI）——TMC5160 の構成/診断インターフェース、または他の SPI 構成可能なチップ向け |
| 1 | 汎用 GPIO（将来のアドオンが高速なセンサー応答を必要とする場合、例えばエンドストップ向けの EXTI 対応割り込み入力） |
| 1 | TMC5160 DIAG0（失速/障害診断ライン、`0x182`/`0x183` 経由でポーリング） |

合計 20 ピン。

**意図的に分離された 2 つの I2C バス：** OLED/F-RAM はこのチップの唯一使用可能なハードウェア I2C ペリフェラル（PA9/PA10 上の I2C2）を使用します。拡張コネクタは独自の、独立したビットバンギング I2C バス（PB10/PB11——このチップの他に I2C 対応可能なピンペアはすでに他の機能に割り当てられていたため、ビットバンギングがハードウェアの競合なしにこのコネクタに独自バスを与える方法でした）を取得します。拡張ヘッダーにぶら下がるもの（I2C ADC/DAC、ポートエクスパンダー、特定のアドオンボードが必要とするもの）は、他の拡張側 I2C デバイスとこのビットバンギングバスを共有しますが、OLED 自身の独立したハードウェア I2C2 バス上のタイミングをクロックストレッチしたり、他の方法で妨害したりすることはできません。

**TMC2209 か TMC5160 のどちらか一方で、必ずしも両方は必要ありません。** どちらのチップも実際の動作には同じ STEP/DIR/EN インターフェースを使用するため、その部分は共通です。異なるのは構成/診断です：TMC2209 はそのために独自のシングルワイヤ UART を使用し、TMC5160 は SPI を使用します——両者は任意の拡張ボード上で相互排他的であるため、4 つの SPI ピンは、SPI バスと同時に使用されることのない別の専用ピンを必要とすることなく、TMC2209 の単一の UART ラインの自然な収容先も兼ねます。ビットバンギング SPI バスは、TMC5160 が期待する正確なプロトコル（SPI モード 3、MSB ファースト、トランザクション全体を通して CS がローに保持される——それを駆動する汎用のバイトパススルーコマンドは `docs/CANBUS.TXT` の `0x180`/`0x181` を参照）を話すため、本ファームウェアがそのチップの特定のレジスタレイアウトを知る必要はありません。TMC5160 の DIAG0 失速/障害ラインも配線されています（`0x182`/`0x183`）——これは、まさにこの種の高速な割り込み駆動入力のためにすでに確保されていた 2 つの汎用 GPIO ピンのうちの 1 つを再利用しています。

このチップの 48 ピンパッケージが持ついくつかのレイアウト制約の背後にある理由を含め、どの MCU ピンがどの信号を担っているかというピン単位の完全な詳細は、`docs/PINOUT_CONNECTORS.TXT` および `src/F303-master/README.md` にあります。

### 6 種類の拡張ボードバリエーション

6 種類の拡張ボードバリエーションのうち 4 種類はステッピングドライバーを搭載しています——TMC2209（コイルあたり最大 2A、パワー MOSFET 内蔵）か、TMC5160A（コイルあたり最大 10A 以上、ドライバー自体には含まれない 8 個の外部パワー MOSFET が必要）のいずれかです。そのドライバーの選択とは独立して、ドライバーを搭載したボードは、**ベーシック**（ドライバー + コネクタのみ、MCU なし——STEP/DIR/EN はメインボードから直接ルーティング）か、**アドバンスド**（第 2 のマイクロコントローラー STM32F303CBT6、2 つのローカルセンサーチップ——16 ビット ADS1115 ADC と MLX9064x 系サーマルカメラ——を追加し、ケーブル経由でルーティングするのではなくツールヘッドで直接生成する必要のあるタイミングを持つツール向けのローカル PWM 生成も追加）のいずれかです。2×2 の組み合わせに加えて、これら 2 つのチップのうち 1 つだけを必要とし、アドバンスドボードが搭載する他の何も必要としないツール向けに、センサーのみのベーシックボード（ADS1115 または MLX9064x、ドライバーもスレーブ MCU もなく、メインボード自身の STM32F303CC に直接配線）が 2 種類追加され——合計 6 枚のボード——`BOM/BOM_EXPANSION_*.TXT`（6 ファイル）、`docs/EXPANSION.TXT`、`docs/PINOUT_SLAVE.txt` を参照してください。

アドバンスドバリエーション自身の STM32F303CBT6 は、上記の拡張コネクタの既存のビットバンギング I2C バス経由でメインボードと通信します——メインボードがマスター、スレーブチップが実際のハードウェア I2C スレーブとして応答します——そして、2 つのセンサーチップ用に、自身の第 2 のローカル専用 I2C バスを駆動します。それは自身のブートローダーとアプリケーションファームウェアを持ち、メインボードと同じ方法（`URTC Flasher` からの CAN-OTA）で更新されますが、スレーブチップへ直接到達するのではなく、その I2C リンクを介して中継されます。完全な技術詳細は `src/F303-slave/README.md` と `src/F303-slave/boot/README.md` を参照してください。

## 💾 パラメータの永続化

板載の FM24CL64B F-RAM（64Kbit、I2C）は、アクティブなツールの設定値とグローバルな LED/OLED 設定の定期的に更新されるスナップショットを保持しているため、突然の電源喪失によって「このボードが何をしていたか」が、その喪失自体が予期しないものであったのと同じくらい知り得ないものになることはありません。それは独自の I2C バスを取得するのではなく、OLED のハードウェア I2C2 バスを共有します——この MCU には、この目的で使用可能なハードウェア I2C ペリフェラルが 1 つしかなく、すでに OLED によって使用されています（完全な理由は `src/F303-master/README.md` 第 6 節を参照）。

**復元された状態は照会可能ですが、危険なものに自動的に適用されることは決してありません。** 起動時、保存されていたものは何でも CAN 経由で読み取り可能になります（`0x190`/`0x191`）——しかし、ヒーターの設定値、レーザー出力、またはモーターコマンドが、それ自体で静かに再起動されることは決してありません。安全で受動的な設定（LED の色、OLED モード）のみが直接復元されます。実際に何が起こったかを確認した後に設定値を意図的に再送信するかどうかは、電源が戻った瞬間にこのボード自体が決めることではなく、マスターコントローラーの判断に委ねられています。

## 💼 ネイティブに自動化されたツールカタログ（25 種類のファームウェアプロファイル）

その動的な切り替えロジックを通じて、ファームウェアは以下のツールヘッドをネイティブに管理します：

1. **はんだ付けステーション（T12）：** 標準的な T12 はんだごて先を扱うための、直接 ADC フィードバックを使用した精密な PID 温度制御に加え、はんだワイヤを接合部へ送り込む電動ワイヤーフィーダー（下記の単純な動作系ツールと `CONN_MOT` およびそのステッピングプロトコルを共有——そのためのスペースを確保するため、このツール自身の汎用エンドストップ入力を犠牲にしています）。[ジャンパー/配線設定 →](images/TOOL_SOLDERING_IRON.png)
2. **SMT はんだペーストディスペンサー：** PCB 上への精密なはんだペースト塗布のためのミリメートル単位の送り制御。[ジャンパー/配線設定 →](images/TOOL_PASTE_DISPENSER.png)
3. **サーマルペースト／液体ディスペンサー：** 高粘度ペーストまたは液体接着剤の流動性管理。[ジャンパー/配線設定 →](images/TOOL_LIQUID_DISPENSER.png)
4. **スマート電動ドライバー：** トルク制限またはエンドストップに基づく回転および停止制御。[ジャンパー/配線設定 →](images/TOOL_SCREWDRIVER.png)
5. **真空／空圧グリッパー：** 安全なピック＆プレース作業のための真空ポンプ制御と圧力レベル読み取り。[ジャンパー/配線設定 →](images/TOOL_VACUUM_PICKUP.png)
6. **ドリル（BL4260）：** ステッピングツールドライバーのイネーブルとは独立した専用のイネーブル/ブレーキラインでの、リアルタイム RPM 読み取りを伴う PWM 速度制御、方向切り替え、動的電子ブレーキ。汎用エンドストップ入力が利用可能。[ジャンパー/配線設定 →](images/TOOL_DRILL.png)
7. **ジンバルグリッパー：** 3 相ブラシレスジンバルモーターを使用した高感度な操作。[ジャンパー/配線設定 →](images/TOOL_GRIPPER_GIMBAL.png)
8. **NEMA グリッパー：** 高負荷ステッピングモーターで制御される堅牢な把持力。[ジャンパー/配線設定 →](images/TOOL_GRIPPER_NEMA.png)
9. **AOI（自動光学検査）システム：** マシンビジョンカメラの撮影のための LED 照明アレイの同期ストロボ制御。汎用エンドストップ入力が利用可能。[ジャンパー/配線設定 →](images/TOOL_AOI_INSPECTION.png)
10. **彫刻レーザーダイオード（10W 光学）：** ホスト通信が失われた場合にロックダウンする安全ハードウェアループ（CAN ウォッチドッグ）を備えた PWM ビーム出力変調。汎用エンドストップ入力が利用可能。[ジャンパー/配線設定 →](images/TOOL_LASER_ENGRAVER.png)
11. **3D プリンティングホットエンド：** 加熱カートリッジの PID 制御、NTC サーミスタの読み取り、エクストルーダー制御、そして専用の 25kHz PWM 制御レイヤー冷却ファン（4 線式、タコメーターフィードバック、独自の通信ウォッチドッグ）——すべてが 1 つのブロックに統合されています。[ジャンパー/配線設定 →](images/TOOL_3D_PRINTER.png)
12. **3D スキャナープローブ：** 遅延のないリアルタイムの表面デジタル化と衝撃検知のための、絶対優先度を持つ超高速ハードウェア割り込み入力（EXTI）。計量用のタッチプロービングも対象——同じハードウェアパスで、同じツールヘッド上の異なる物理プローブです。[ジャンパー/配線設定 →](images/TOOL_SCAN_PROBE.png)
13. **SMT ピック＆プレースヘッド：** 上記のペースト/液体ディスペンサーと両方のグリッパーと同じステッピングインターフェース上での、正しいパッド位置合わせのための回転 A 軸。[ジャンパー/配線設定 →](images/TOOL_SMT_PICKPLACE.png)
14. **重量物用電磁石：** 汎用 GPIO ドライバーとして転用された T12 ヒーター出力を使用した、強磁性部品のオン/オフ吸着制御。[ジャンパー/配線設定 →](images/TOOL_ELECTROMAGNET.png)

## 🖥️ ローカル OLED インターフェース

すべてのツールヘッドは、128×64 の 2 トーン OLED 上に、ライブでツール固有のテレメトリを表示します：電源投入時のアニメーション起動スプラッシュ、点滅する CAN アクティビティインジケーター、上部ストリップのライブな「主要」読み取り値（温度、RPM、電力——アクティブなツールにとって最も重要なもの）、そしてツールプロファイルごとの小さな 4 フレームアニメーションアイコン。

### モジュール

下記の 2 つの物理バリエーションは、電気的には同じパネルです（SSD1306 または SSD1315 駆動——ファームウェアの初期化シーケンスは両方と互換性があることが確認済みです。`firmware_oled_driver.c` の `OLED_Init()` を参照してください。SSD1315 は新しい、そのまま置き換え可能なコントローラーで、今日多くのモジュールが同じ「SSD1306」表記/シルク印刷の下で実際にはこれを出荷しています）、いずれも **128×64**、そして同じ 2 トーンの「黄/青」分割で、物理的な LED 素材自体が 2 つの固定色ゾーンに分かれています（これはソフトウェアで選択できるものではありません）：

* **上部 16 ピクセル（0-1 ページ）：黄色。** URTC はこのストリップを、詳しく読まなくても一目でわかる最も有用な情報——CAN アクティビティインジケーター、ライブな主要読み取り値、または（起動スプラッシュ/無効ツール画面では）短いステータステキスト——のために使用します。
* **下部 48 ピクセル（2-7 ページ）：青色。** その他すべて——ツールアイコン、詳細なテレメトリ、スプラッシュ画面上のアニメーション JuanenBOT の顔、大きく点滅する ERROR のワードマーク。

どちらも同じ I2C2 バスと同じ `OLED_Init()` に接続されます——ファームウェアはどちらが取り付けられているかを判別できず、判別する必要もありません。両者は特定のボード上で相互排他的です（`BOM/BOM.TXT` の `CONN_OLED2` の注記を参照——本ドキュメントでの、回路図が `LCD1` と呼ぶものの名前です）。

#### オプション A ——直接実装（`CONN_OLED2`、実際にボードに実装されているフットプリント）

<img src="images/OLED_DIRECT_MOUNT.jpg" width="220">

独立したブレークアウト PCB を持たない裸のパネル——ガラス板とその 30 ピン FPC リボンだけが、`CONN_OLED2` フットプリント（`FPC30`、WiseChip UG-2864、本ドキュメントでの、回路図が `LCD1` と呼ぶものの名前——`BOM/BOM.TXT` と `URTC_NETLIST.TXT` を参照）に直接はんだ付けされています。30 ピンのうち、実際に配線されているのは一部だけです——残りはパネルの並列インターフェースバス（`D2`–`D7`、`RW`、`E/!RD`）で、本ボードは I2C 経由でのみそれと通信するため、未接続のままです：

| CONN_OLED2 ピン | ネット | 機能 |
|---|---|---|
| 1, 8, 29, 30 | GND / AGND | グラウンド |
| 9 | VDD | ロジック電源（`+3V3B`、OLED 専用のレールから——BOM §1 参照） |
| 28 | VCC | パネル電源 |
| 2–5 | C2P/C2N/C1P/C1N | チャージポンプコンデンサー——BOM の `C26`/`C27` |
| 26 | IREF | 基準電流設定抵抗 |
| 27 | VCOMH | 内部共通電圧デカップリング |
| 10, 12 | BS0, BS2 | GND に接続 |
| 11 | BS1 | `+3V3B` に接続 |
| 18 | D0/SCK | I2C2 SCL——PA9 |
| 19 | D1/DIN/SDA | I2C2 SDA——PA10 |

`BS0`/`BS1`/`BS2` は、パネル自身のインターフェース選択ストラップ（ここでは GND/VCC/GND）であり、MCU に公開されるのではなくハードウェアで固定されています——これによって、他の 22 個の FPC ピンが属する 8080/6800 パラレルモードではなく、まずコントローラーが I2C モードになります。

#### オプション B ——ブレークアウトモジュール（`CONN_OLED`、外部代替案）

## 🔴🟢🔵 デジタルステータス LED

OLED および 8 ピクセルの照明リングとは別に、`CONN_LED1` は、一目でわかるステータス専用の単一のアドレス指定可能な RGB LED（WS2812B 系、SPI/DMA 駆動）を運びます。

**デフォルトでは自動、必要に応じてホストが上書き可能。** ファームウェアはこの LED の色を独自に、3 段階の優先順位で決定します：

* 🔴 **赤** ——ハードウェア障害がアクティブ（`system_error_flag`）。他に何が起きていようと、常に優先されます。
* 🔵 **青** ——ボードが積極的に機能中：過去 1.5 秒以内に CAN フレーム（任意の ID）が到着しました。
* 🟢 **緑** ——アイドル、コマンド待ち：1.5 秒以上 CAN トラフィックがありません。

マスターは、CAN ID `0x100`（DLC 8）を送信することで、いつでもこれを上書きできます。最初の 3 バイトが赤、緑、青の強度です（それぞれ 0-255——自動の 3 色だけでなく、完全な 24 ビットカラー）。ホストが送信した色は 10 秒間保持された後、自動方式にフォールバックします——実際に見えるほど十分に長く、ホストが更新を止めた場合にボードが古いカスタムカラーの表示に固定されないほど十分に短い時間です。`0x100` を再度送信する（同じ色でも新しい色でも）と、その 10 秒のウィンドウがリフレッシュされるため、カスタム制御を維持したいホストは定期的に送信し続けるだけで済みます。ハードウェア障害は、アクティブなオーバーライドを常に中断します——赤は、ホストが設定したどの色よりも優先されます。

正確なバイトレイアウトは `docs/CANBUS.TXT`（ID `0x100`）を参照してください。このメッセージは、リング LED および OLED の夜間モード制御とも共有されています。

## 🔧 ビルドと書き込み

URTC のフラッシュは 2 つの独立した部分に分割されているため、本ボードはすでに他のすべてに使用しているのと同じ CAN 臍帯ケーブル経由で再書き込みできます——初期セットアップの後は、JTAG/SWD ヘッダーに物理的にアクセスする必要は二度とありません。

### フラッシュメモリレイアウト（合計 256K、ゴールデンイメージ / A-B 更新モデル）

```
0x08000000 ┌─────────────────────────────────┐
           │  ブートローダー（30K）             │  すべての起動時に常に最初に実行。
           │                                   │  CAN で短時間リッスンし、その後
           │                                   │  アプリへジャンプするか、更新を
           │                                   │  待機する。更新中は OLED を直接
           │                                   │  駆動する（下記参照）。
0x08007800 ├─────────────────────────────────┤
           │  メタデータページ（2K）            │  現在メインスロットにある
           │                                   │  内容を記述：HardwareID、
           │                                   │  バージョン、サイズ、CRC32、
           │                                   │  そして HMAC-SHA256 署名。
           │                                   │  ブートローダーはアプリへ
           │                                   │  ジャンプする前に、これら
           │                                   │  すべてをチェックする。
0x08008000 ├─────────────────────────────────┤
           │  メインスロット（112K）            │  これはアプリケーション
           │                                   │  ファームウェア /
           │                                   │  URTC_MAIN_FIRMWARE_v0.2.7.* ——
           │                                   │  日々実行される実際の
           │                                   │  ファームウェアで、本
           │                                   │  README の他の場所で
           │                                   │  説明されているものです。
           │                                   │  検証済みの正常なイメージが
           │                                   │  それを置き換える準備が
           │                                   │  できるまで、更新によって
           │                                   │  触れられることはありません。
0x08024000 ├─────────────────────────────────┤
           │  バックアップ/ステージングスロット   │  生ストレージのみで、
           │  （112K）                          │  直接実行されることは
           │                                   │  ありません。すべての CAN
           │                                   │  更新は、まずここに書き込まれます。
0x08040000 └─────────────────────────────────┘
```

**バックアップスロットが必要な理由。** CAN 更新は、現在実行中のスロットに書き込まれることは決してありません。まずバックアップに書き込まれ、そこで完全に検証されます——サイズ、CRC32、そしてそれが単に完全に到着しただけでなく、本当に本プロジェクト自身のビルドプロセスから来たものであることを証明する HMAC-SHA256 署名——そしてその後にのみメインスロットへコピーされます。そのコピーが始まる前のどの時点で電源が失われても、現在実行中のファームウェアはまったく影響を受けないままです。そのため、中断されたダウンロードがボードをブリックさせてしまうウィンドウは存在しません。もしコピー*自体*の最中に電源が失われた場合、ブートローダーは次回の起動時にそれに気づき（バックアップはコピー中に決して触れられないため、依然として完全に無傷です）、成功するまでそこからコピーを単純に再開します。

### 0. ソースからのコンパイル（任意——`firmware/` にはすでにビルド済みバイナリが同梱されています）

本リポジトリのソースから上記 4 つのバイナリを得るには 2 つの方法があります：

- **自動化：** リポジトリルートの `build_firmware.sh`（Linux）または `build_firmware.bat`（Windows）。どちらも、ARM GNU ツールチェーンが不足していればインストールし、固定バージョンの ST HAL/CMSIS コミットを取得し、4 つのバイナリすべて（メインボードアプリ + ブートローダー、拡張スレーブアプリ + ブートローダー）をコンパイル、リンク、`objcopy` して `firmware/` へ直接出力し、その後 `firmware/firmware_manifest.json` を再生成します。引数なしで実行すると完全なビルド、`--clean` でまずローカルの `build/` キャッシュを消去、または `master`/`slave` で 1 つのチップ自身のペアのみをビルドします。`build_firmware.sh` は本プロジェクトの実際のソースツリーに対してエンドツーエンドで実行されます。`build_firmware.bat` は Windows 向けに同じロジックをミラーリングします——もし両者が食い違った場合は、`.sh` スクリプトのロジックをリファレンスとして信頼してください。
- **手動：** どちらのスクリプトが実行するすべてのコマンド、そして各ツールチェーン/HAL の選択の背後にある理由が、`docs/COMPILE_STM32F303.TXT` にステップバイステップで詳しく書かれています——異なる OS、異なる HAL/CMSIS ソースで作業する場合、あるいは単にスクリプトが自動化していることを正確に確認したい場合に役立ちます。

ファームウェアのソースを変更した後（またはバージョンの加算を信頼する前に）、リポジトリルートから **`check_version_consistency.sh`** を実行してください：これは Track A/E のバージョン定数（メインボードファームウェア、拡張スレーブアプリケーション）を真実の源として読み取り、`VERSION_CHECKLIST.txt` がそのバージョンタグについて記録しているすべての場所をチェックし、不一致を報告します——報告するだけで、自分で何かを修正することはありません。`VERSION_CHECKLIST.txt` は、本プロジェクトが持つ 5 つの独立したバージョントラック（メインファームウェア、ハードウェア/PCB、メインブートローダー、拡張スレーブアプリケーション、拡張スレーブブートローダー）すべての完全なリファレンスであり、そのいずれかを加算する際に正確に何を変更する必要があるかを示します。

### 1. 初回セットアップ——JTAG/SWD が必要（一度だけ）

ブートローダーは物理的なプログラミングによってのみチップに載せることができます——まだブートローダーが載っていないボードを CAN でフラッシュする方法はありません。これは一度限りのステップです：

1. **STM32CubeIDE**（STM32F303CC ターゲットに対してビルド・テスト済み）でプロジェクトを開くか、下記のコンパイル済み出力を使って **STM32CubeProgrammer** を直接使用します。
2. 板載の `STM_JTAG` ヘッダー経由で、SWD（ST-Link）で**両方の**イメージを書き込みます——各 `.hex` ファイルにはターゲットアドレスが焼き込まれているため、（STM32CubeProgrammer を含む）ほとんどのツールは同じセッションで両方を読み込めます：
   * `URTC_MAIN_BOOTLOADER_v0.3.6.hex` → `0x08000000`
   * `URTC_MAIN_FIRMWARE_v0.2.7.hex` → `0x08008000`
3. 電源を入れる前に、ID はんだジャンパーでツールの識別情報を設定します——ボードは起動時に一度だけそれを読み取ります、いつもどおりです。5 つのジャンパー（ID0-ID4）で、完全な 32 アドレス空間をカバーします（31 の直接ツールアドレスに加え、予約された `11111` のフリー構成アドレス——上記のツールマトリクスの節を参照）。
4. 電源を入れます。ブートローダーは約 600ms リッスンし、何も見つからず、直接アプリケーションへジャンプします——ここから先は、すべてが本 README の残りの部分で説明されているとおりに動作します。

**JTAG ヘッダーが取り外されたり無効化されたりすることは決してありません。** それは常にフォールバックとして存在します——もし CAN 更新がうまくいかなかった場合、あるいは単にそちらを好む場合、いつでも SWD 経由でどちらかのイメージを再書き込みできます。

**ボード上の 2 つのプッシュボタン、BOOT と RESET** も復旧のために存在します——RESET は通常のハードウェアリセット（`NRST`）で、BOOT は `BOOT0` をハイに引き上げます。これは、本リポジトリ内の何かが実行される*前に*チップレベルで下される決定です：通常（押されていない場合）はチップはフラッシュから起動し、上記のように本プロジェクト自身のブートローダーに入ります。リセット時に押されていると、代わりに ST 自身の工場出荷時のシステムメモリブートローダー（USB DFU/UART 復旧、ここにあるものとは完全に別のもの）で起動します。完全な技術詳細は `src/F303-master/README.md` 第 4a 節を参照してください。

### 2. 以降の更新——CAN バス経由

ブートローダーが設置されると、アプリケーションの更新にはもはやボードへの物理的なアクセスは一切不要になります——ツールヘッドへのコマンドをすでに運んでいるのと同じ臍帯 CAN ライン経由で新しいファームウェアビルドを送信するだけです。

**更新シーケンス：**

1. **トリガー。** マスターは*実行中のアプリケーション*へ `0x7F0`（DLC 4、ペイロード `B0 07 1D 5A`）を送信します。これは、モーター、ヒーター、レーザーといったすべてのアクチュエータへの電源をインラインで安全に遮断し、チップをリセットします。この魔法のペイロード要件は、破損した、あるいは不正な形式のフレームが誤って更新モードへのリセットをトリガーできないことを意味します。
2. **開始。** リセット後、ブートローダーがリッスンしています。マスターは `0x7F1`（DLC 8、ビッグエンディアンのファームウェア総サイズ + ビッグエンディアンの HardwareID）を送信します。異なるハードウェア向けにビルドされたイメージは、フラッシュの 1 バイトも触れられる前に、まさにこの時点で拒否されます。ブートローダーは新しいイメージが必要とする分だけ正確にバックアップスロットのページを消去し、ステータスフレーム（`0x7F5`）で応答します。
3. **署名。** マスターは、期待される HMAC-SHA256 署名を、4 つの `0x7F7` フレーム（それぞれ 8 バイト、順序どおり）として送信します——これは、ブートローダーとビルドに署名するツールの間で共有される鍵を使い、ファームウェアイメージに対して計算されます。
4. **データ。** マスターは `.bin` ファイルを、連続して送信される一連の `0x7F2` フレーム（それぞれ最大 8 バイトの生ファームウェアデータ）としてストリーミングします——CAN は単一バス上でフレームが送信された順序で到着することを保証するため、フレームごとのシーケンス番号は不要です。ブートローダーは受信バイトを RAM 内の 2KB ページにバッファリングし、満杯になったら*バックアップ*スロットに書き込み、そのページが完了したと見なす前に、書き込まれるはずだった内容と比較しながら各ハーフワードを読み戻し、検証済みの書き込みごとに（ページインデックス付きの）`0x7F3` 確認応答を送信します。妥当なマスター実装は、次のページ分のデータを送信する前に各ページの ACK を待ち、ブートローダーの受信バッファをオーバーランさせないようにします。
5. **終了と検証。** すべてのバイトが送信されると、マスターは `0x7F4`（DLC 8、ビッグエンディアンの CRC32 + メジャー/マイナーバージョン）を送信します。ブートローダーはバックアップスロットのサイズをチェックし、その CRC32 と HMAC-SHA256 を計算し、両方をマスターが宣言した値と比較します。すべてが一致した場合にのみ、上記と同じ読み戻し検証を伴って、ページごとにバックアップをメインスロットへコピーする処理を進めます。そのコピーが完了して確認されると、新しいメタデータを保存し、更新されたアプリケーションへリセットします。サイズ、CRC32、HMAC、または HardwareID のいずれかが不一致の場合、メインスロットはまったく触れられず、ブートローダーは単に新しい試行のためのリッスンに戻ります。

**ステータスフレーム（`0x7F5`、DLC 1）：** `0x01` リッスン中、`0x02` 消去中、`0x03` 受信中、`0x06` 検証中、`0x07` バックアップをメインへコピー中、`0x04` 検証成功（ジャンプ直前）、`0x05` 検証失敗、`0xFF` エラー。

**ハートビート（`0x7F6`、DLC 2、リッスンまたは更新中は約 1 秒ごと）：** ステータスバイト + 進捗パーセント（0-100、パーセントが適用されない場合は `0xFF`）。マスターが「ノードは生きているがまだリッスンを開始していない」を「ノードが完全に応答していない」と区別できるようにします——自動化された立ち上げや、タイムアウトを待たずに止まったブートローダーを発見するのに便利です。

**画面上の進捗。** ブートローダーは更新中に OLED を直接駆動します——何が起きているかを誰も推測する必要はありません。ページが書き込まれたりコピーされたりしている間は「UPDATING」とライブの進捗バーおよびパーセンテージを表示し、新しいファームウェアへリセットする直前に一瞬「FLASH OK」を表示し、ページの書き込みが失敗した場合、転送が 10 秒以上停滞した場合、または検証が不一致で返ってきた場合には「ERROR」を表示します。

**⚠️ 信頼する前に実験台でテストしてください。** 上記のプロトコルはクリーンにコンパイル・リンクされ、ロジックも慎重に検討されていますが、ブートローダーはまさに「正しくビルドされる」ことと「ハードウェア上で信頼できる」こととの間に大きな隔たりがあるタイプのファームウェアです——実際のフラッシュプログラミングのタイミング、数千フレームにわたる転送での CAN の挙動、そしてブートローダーからアプリケーションへの引き継ぎは、実際のアクチュエータが接続された無人更新でこれに頼る前に、実機ボード（できれば JTAG を手元にフォールバックとして）で検証される必要があります。

## 📋 変更履歴

ファームウェアとブートローダーは独立してバージョン管理・リリースされます——新しいブートローダーを書き込んでも新しいアプリケーションバージョンを意味するわけではなく、その逆も同様であるため、それぞれが常に一緒に動くことを示唆する 1 つの結合されたバージョン番号ではなく、それぞれ自身のファイルに自身の履歴を持ちます：

- ファームウェア（`src/F303-master/`）：[`src/F303-master/CHANGELOG.md`](src/F303-master/CHANGELOG.md)
- ブートローダー（`src/F303-master/boot/`）：[`src/F303-master/boot/CHANGELOG.md`](src/F303-master/boot/CHANGELOG.md)
- 拡張スレーブアプリケーション（`src/F303-slave/`、STM32F303CBT6）：[`src/F303-slave/CHANGELOG.md`](src/F303-slave/CHANGELOG.md)
- 拡張スレーブブートローダー（`src/F303-slave/boot/`）：[`src/F303-slave/boot/CHANGELOG.md`](src/F303-slave/boot/CHANGELOG.md)

**バージョン管理ポリシー：** 4 つのコンポーネントすべて（2 つのアプリケーションファームウェア、2 つのブートローダー——`FIRMWARE_VERSION_MAJOR`/`MINOR`/`PATCH` および `BOOTLOADER_VERSION_MAJOR`/`MINOR`/`PATCH`）は**インクリメンタル**です——実際のビルドのたびに、そのコンポーネント自身の `PATCH` が自動的に 1 つ加算され（リポジトリルートの `bump_version.py`、各コンポーネントをコンパイルする直前に `build_firmware.sh`/`.bat` から呼び出されます）、`PATCH` が 9 を超えると `MINOR`（その後 `MAJOR`）へ繰り上がります。これは、車自身のオドメーターが使用するのと同じ 10 進法の「オドメーター」ルールです——例：`0.1.7` → `0.1.8` → `0.1.9` → `0.2.0`、決して `0.1.10` にはなりません。各ブートローダーも、対応するアプリケーションの `FIRMWARE_VERSION_*` の自身のコピーを保持し、同じ加算によって自動的に同期が保たれます。4 つのコンポーネントすべての現在のバージョンを一目で確認するには、リポジトリルートの [`CHANGELOG.md`](CHANGELOG.md) を、トラックごとの完全なメカニズムは [`VERSION_CHECKLIST.txt`](VERSION_CHECKLIST.txt) を参照してください。

## 🔍 現在の状態

**ファームウェア（`src/F303-master/`）：** 全 25 種類のツールプロファイルで機能完全——熱 PID 制御、ツールごとのテレメトリ、通信ウォッチドッグ、失速/障害検出、そして OLED 自身のライブ診断に加え、アクティブツール照会ペア（`0x110`/`0x111`）、拡張コネクタ向けの汎用 SPI パススルー（`0x180`/`0x181`）、電源喪失時にも設定値を保持する板載 F-RAM（`0x190`/`0x191`）、`11111` ジャンパーのフリーツール構成メカニズム（`0x1A2`/`0x1A3`）、共有バス上で複数の（それ以外は同一の）ボードを区別するための周辺機器タイプ + デバイスシリアル番号レポート（`0x1A4`/`0x1A5`）、そしてアドバンスド拡張ボード上の拡張スレーブチップに到達する CAN-to-I2C ブリッジ（`0x210`-`0x221`）。ブートローダーとは独立してバージョン管理されています（下記の変更履歴を参照）。

**ブートローダー（`src/F303-master/boot/`）：** 機能完全なゴールデンイメージ A/B 更新システム——CAN 経由の HMAC-SHA256 署名付き OTA 更新、失敗した更新が決してボードをブリックさせないことを保証するバックアップスロット、そしてアプリケーションとは独立した自身のバージョンレポート（`0x7FA`）。クリーンにコンパイル・リンクされます。実際のアクチュエータが接続された無人環境でこれを信頼する前に、上記の実験台テストの注意事項を参照してください。

**PC ツール：** [URTC Flasher](https://github.com/JuanenRac/URTC-FLASHER)（CAN OTA 更新 + フルチップ SWD/JTAG プログラミング）と [URTC Tester](https://github.com/JuanenRac/URTC-TESTER)（ライブなツールごとの制御/テレメトリテスター）の両方は、それぞれが目指したことについて機能完全であり、今ではそれぞれが独立したプロジェクトとなり、セットアップとすべてのコントロールを詳しくカバーする独自の README を持っています。

**ハードウェア：** 回路図と BOM はまだ最終決定されておらず、上記のいずれかを実際のシリコンに対して検証するための実装済みボードはまだ存在しません。上記のすべてはコンパイル・リンクされ、慎重に検討されていますが、「正しくビルドされる」ことと「ハードウェア上で検証済み」であることは 2 つの異なる主張です——本 README の冒頭の安全上の注意を参照し、新しいボードにふさわしい注意をもって初回の立ち上げに臨んでください。
